## 1. 两个不同的基线（必须分清）

N7.3 明确区分**两个**基线，绝不混为一谈：

| 概念 | revision | tree | 含义 |
|---|---|---|---|
| **A. PRODUCT_RUNTIME_BASELINE** | `ef895dc05d641a4c087dd6dfa919dbeb5f2f0dfe` | `a34bfbf7cb43c1f38b77a03e92936024c32316fb` | 被文档描述、被证据担保的**产品运行时** |
| **B. N7_3_HANDOFF_BASELINE** | 最终 N7.3 closure commit | 其 tree | 描述并校验 A 的**文档/证据/测试包** |

**A 不等于 B。** `ReleaseEvidenceV1.attestsTo.productRuntimeRevision` 是 A；B 由
`planning/ai-native-v1/release/N7.3-closure-validation.json` 绑定。

> 不要把 `sourceRevision = ef895dc…` 读成"N7.3 文档包也等于 ef895dc…"。它只表示**生成证据时**的仓库 revision 与工作区状态，属来源记录（provenance）。

### 绑定模型（非自引用）

```
ReleaseEvidenceV1.json
  ├─ attestsTo.productRuntimeRevision / productRuntimeTree   → A（稳定、可独立验证）
  ├─ handoffArtifacts[]                                       → 本文档包各文件的 sha256 + bytes
  └─ （刻意不包含"添加它自身的 commit 哈希"）

ReleaseEvidenceV1.payload.sha256                              → 证据载荷内容的 sha256（由生成器写出）

N7.3-closure-validation.json                                  → 在 N7.3 包提交之后写出，
                                                                 因而可以命名 B 的 commit/tree，
                                                                 并绑定上面的 payload sha256
```

这样不存在**不可满足的循环哈希**：变化的文件不需要包含自身的哈希；需要绑定最终 commit 的记录在 commit 存在之后才写。

### 哈希契约：canonical git blob（PHASE 5-R1）

所有证据哈希绑定 **canonical git blob 内容**，而不是检出后的工作区字节；
统一实现见 `api/lib/evidenceHashing.cjs`（`HASH_CONTRACT = GIT_BLOB_CANONICAL`）。

- 受版本控制的路径：`git cat-file blob <rev>:<path>`，即 git 规范化后入库的字节。
- 尚未提交的路径：对工作区内容做 LF 规范化——这正是 `core.autocrlf=true` 下 git
  会入库的字节，因此与上一分支落在同一个哈希空间。

这样同一个 git revision 在 Windows / macOS / Linux 上得到同一个证据哈希。
**不要**改回直接对 `fs.readFileSync()` 的原始字节求哈希：那样在 CRLF 检出上会得到
不同结果，使 N7.3 存证链无法跨平台验证。

### 因此未来工程师可以证明

1. `ReleaseEvidence` 描述的是产品运行时 `ef895dc…`（A）；
2. N7.3 交接包属于某个**具体的**最终 commit/tree（B，见 closure validation）；
3. 文档/证据文件未发生静默漂移（逐个 `handoffArtifacts[].sha256` 可重算比对）；
4. 不存在循环自哈希声明。

## 生产整合候选补记（PHASE 5-R3）

本交接包在生产整合候选分支 `ai-native/prod-integration-v1` 上被重新绑定，原因与方式记录如下：

- **为什么必须重新绑定**：`docs/api-reference.md` 与 `docs/technical-debt.md` 都是本交接包按 sha256 存证的产物。修正 `qty=0 移除对应角色` 这句当前时态错误，必然改变这两个文件的哈希。
- **非自引用模型保持不变**：
  - `PRODUCT_RUNTIME_BASELINE`：最后一次改动产品运行时的提交（`ReleaseEvidenceV1.attestsTo.productRuntimeRevision`）。
  - `HANDOFF_DOCUMENTATION_PACKAGE`：记录重新生成后证据的提交。
  - `CLOSURE_VALIDATION`：在此之后写入、并指名上述包提交的记录。
  - 三者刻意互不相同；`ReleaseEvidenceV1` 仍然不含“添加它自身的 commit 哈希”。
- **哈希语义**：统一使用 `GIT_BLOB_CANONICAL`（`api/lib/evidenceHashing.cjs`），即 canonical git blob 内容，而不是检出后的工作区字节，因此同一 revision 在 Windows / macOS / Linux 上得到同一证据哈希。
- **不要做的事**：不要为了让本包“看起来没变过”而回退上述文档修正；也不要把历史 `ai-native/v1` 上的已验收证据改写成本候选的内容。
