# 水泵 BOM 订单及生产管理系统

> 当前版本说明，更新于 2026-07-29。本文只描述现行功能与规则；安装、启动和部署命令见项目根目录 [README.md](../README.md)，完整 API 总表见 [api-reference.md](./api-reference.md)，API 开发约束见 [api-sop.md](./api-sop.md)，业务流程基准见 [business-flow.md](./business-flow.md)，线圈领域规则见 [coil-domain.md](./coil-domain.md)，前端状态边界见 [frontend-state-boundary.md](./frontend-state-boundary.md)，UI/交互约束见 [ui-refactor-guidelines.md](./ui-refactor-guidelines.md)。当前开发主线和延期事项见 [开发待办与向量检索主线](./development-backlog.md)，产品化拆分讨论稿见 [通用内核与定制模块拆分设计](./modularization-design.md)。

## 1. 系统用途

系统以水泵 BOM 为核心，统一管理：

- 零件、供应商、库存和实时价格；
- 定子标准直径、俗称、材质、槽眼、绕组方案和铜价成本；
- 泵壳模板、产品配方和历史常用配置预设；
- 客户、报价、订单、采购清单和生产待办；
- 转子参数、自动出图、历史归档和打印；
- AI、语音和 Siri 查询及受控写操作。

核心目标是让配方成本、报价、订单和采购都引用同一套基础数据，减少重复录入和口径差异。

## 2. 业务流程

新增业务、拆页面或调整状态管理前，必须先对照 [业务流程说明](./business-flow.md)、[前端状态边界](./frontend-state-boundary.md) 和 [UI/交互约束](./ui-refactor-guidelines.md)。本节只保留业务主线概览。

```text
维护零件与线圈
  -> 建立泵壳模板
  -> 创建产品配方并保存成本快照
  -> 复制相近配方快速生成同泵壳的其他功率型号
  -> 客户报价
  -> 报价转订单 / 直接创建订单
  -> 展开 BOM 生成采购清单和生产待办
  -> 分批采购、到货、入库与订单关闭
  -> 按模板或订单型号生成转子图纸
```

### 基础数据

- **零件**：按型号、分类、供应商记录价格和库存。同型号可以有多个供应商。包装类使用二级分类：`外包装`（牛皮纸箱、彩印箱、木箱）、`内衬`（泡沫、珍珠棉）和 `固定包材`（说明书、贴纸等）。
- **线圈**：定子组合按标准直径、材质和槽眼建档；绕组方案再记录片数、铁芯单片价、铜重、加工费、默认搭配电缆线径/电容及主副漆包线绕组备忘。正式方案同时维护线圈转子成品库存和流水，测试方案不进入正式成本。
- **系统设置**：业务白名单配置包括管理费、电缆铜套、浮球新界式差价、铝线价格基数和美元兑人民币汇率；`/setup` 系统初始化页维护 AI 与知识检索运行参数，API Key 加密保存，部署安全密钥只显示状态。

### 泵壳模板与历史常用配置

泵壳模板定义一套壳体的固定结构，包括：

- 固定配件或壳体组件；
- `components` 分项计价或 `bundle` 整套计价；
- 安装工资、打包工资和默认表面处理工艺；
- 转子出图默认参数。

计价方式通过“泵壳套件 / 自由搭配”切换：泵壳套件模式必须从零件库“泵壳”分类选择整套型号，默认带入该型号最低有效参考价并允许模板覆盖，同时可填写套件计价备注；自由搭配模式的组合模板名称既可手输，也可从零件库泵壳型号中选择，成本和库存落在每个真实组件上。自由搭配所用组件统一在零件库“泵壳搭配”分类建立，模板中的组件型号只能从该分类下拉选择；组件需维护组件名、零件型号、供应商、数量和是否计入成本，优先按零件库价格计价，未定价时才使用手输单价。机筒组件通过下拉菜单选择“铝机筒 / 不锈钢拉伸筒 / 铁机筒”，其中只有“不锈钢拉伸筒”启用按机筒长度计价，其他两种按普通固定组件处理。两种模式的数据分别保存，不在同一界面混合编辑。零件库泵壳勾选“不锈钢机筒”且模板使用泵壳套件整体价时，套件价以 150mm 机筒为基准，配方机筒长度每增加 10mm 加 1 元，低于或等于 150mm 不倒扣；这笔加价直接计入“泵壳套件”整体成本，不作为独立零件行。模板可预设喷漆、电泳、电泳+喷塑或整体喷塑并录入费用，创建配方时自动带入该表面处理工艺和成本。

常用配置是历史兼容能力，用于保存同一模板下的高频线圈、机筒、长螺丝和叶轮组合；已有数据及 `POST /api/recipes/model-variant-draft` 接口继续保留，但不再作为日常新建配方的必经步骤。新流程直接选择泵壳模板和线圈，再完成浮球、电缆、包装、人工及费用配置；同泵壳的其他功率型号通过复制相近配方后修改线圈生成。长螺丝仍与不锈钢机筒绑定，目标长度 = 机筒长度 + 补偿长度；机筒长度和补偿长度均随配方持久化，重新编辑时恢复原值。泵壳套件模式由零件库泵壳“不锈钢机筒”元数据触发，自由搭配模式由“不锈钢拉伸筒”组件类型触发。铝机筒、铁机筒按普通零件型号和库存处理。

### 产品配方

配方是一台产品的完整 BOM 与成本快照，包含：

- 模板固定配件、额外配件；
- 线圈俗称/标准直径、片数、材质和槽眼；
- 浮球线径/铜套类型、电缆长度/线径/铜套类型；
- 包装材料；
- 安装、打包、表面处理和管理费；
- 机筒长度、叶轮参数和技术档案；技术档案内集中维护上/下轴承、转子片数、转子直径、开档、定位、油封孔径、叶轮孔径/开档/厚度和螺纹尺寸，转子出图页选择配方后自动带入；已有配方可上传 `.xls/.xlsx` 水泵性能测试报告，原文件与解析结果保存在 SQLite。

配方页以“泵壳模板 + 线圈配置 + 客户选配”为唯一可见主流程：泵壳模板提供结构成本包，线圈配置联动电容、电缆/浮球线径和叶轮参考，客户选配再覆盖电缆长度、浮球、包装材料、接轴和表面处理等 OEM 差异。需要复用时直接复制已有配方，不要求用户理解或维护额外的常用配置层级。

BOM 草稿由 `POST /api/recipes/bom-draft` 统一生成。前端展示零件时必须使用草稿中的 `snapshotPrice`、`costSource/source` 和 `formula` 标注成本价与计算来源；不得在页面里另写正式成本公式。配方保存前，后端会逐项检查完整 BOM 的快照单价；任何项目价格缺失、无效或为 0 都会阻止保存并列出具体项目，避免浮球、电缆等自动匹配失败后漏算成本。客户指定线重使用配方字段 `coilWireWeight` 进入 BOM 草稿，由后端线圈服务重算成本并自动关联电容。叶轮参数只属于技术档案和出图参考，不参与成本计算。

表面处理支持：无、喷漆、电泳、喷塑。旧 `paintingWage` 字段只用于历史数据兼容，新逻辑使用 `surfaceTreatmentMode + surfaceTreatmentCost`。

### 报价、订单与采购

- 客户默认利润率按小数保存（`0.10` 表示 `10%`）；生成报价时转换为 `1.10` 倍售价，系统未配置时默认利润率为 `10%`。
- 报价以配方保存成本为锁定基线。客户只允许调整是否带浮球、电缆米数、纸箱/木箱、泡沫和珍珠棉；线圈、浮球/电缆线径、普通/新界式铜套、表面处理、机筒长度及固定 BOM 均沿用配方。
- 组合包材按完整有效清单保存：外包装在纸箱/木箱中选择，泡沫和珍珠棉独立启用，说明书、贴纸等固定包材继续沿用。
- 报价界面使用利润率百分比（如 10%），保存及价格计算仍兼容历史加价倍数（如 1.10）。
- 报价保存前通过 `POST /api/quotations/save-payload-draft` 由后端重新试算，统一生成含完整 BOM/成本快照的 `itemsJson`、`totalCost` 和 `totalPrice`。
- “报价中”超过一个月的报价在列表读取时自动标记为“已过时”。
- 报价按 `草稿 → 报价中 → 已接受 → 已转订单` 流转；已拒绝、已转订单和已过时为终态，只有已接受报价可以通过事务接口转单。
- 报价转订单先通过 `POST /api/quotations/:id/order-draft` 预览，再调用 `POST /api/quotations/:id/convert` 在同一事务内创建订单、关联报价并更新状态，重复或越级转单会被拒绝。
- 订单保存前通过 `POST /api/orders/save-payload-draft` 统一生成 `itemsJson`、`purchaseListJson` 和 `todosJson`。
- 直接创建的订单先进入“待确认”；确认后才可登记采购进度。采购中和采购完成由采购数量自动推导，采购完成后仍需人工关闭订单。
- 采购项记录计划、下单、到货、入库数量、采购单价、实际供应商和时间；数量必须满足 `入库 ≤ 到货 ≤ 下单`，超采需要明确确认。
- `POST /api/orders/:id/purchase-items/progress` 支持部分采购、部分到货和分批入库；只有入库增量会在同一事务内增加对应库存，并写入采购项批次历史。
- `POST /api/orders/:id/complete-purchase` 保留为一次性全部到货入库动作，执行后只进入“采购完成”，不会直接关闭订单。
- 一键入库确认同时列出普通零件、正式线圈和非库存计算项；零件与线圈分别写入各自库存，非库存项只推进采购进度。采购入库不等于生产领料，订单关闭不会自动扣库存，实际领用继续走库存页面人工出库。
- `GET /api/orders/:id/readiness` 只读执行订单生产准备检查；复用活动订单库存平衡结果，依次核对订单、BOM、零件、线圈、采购和成本价格。已下单或到货不能替代入库库存，只有当前可用库存覆盖需求时才返回可生产。
- `GET /api/orders/readiness-overview` 一次计算全部活动订单的库存平衡和生产准备结论，汇总数据阻塞、待补料、待复核、可生产数量，并返回各订单主要问题和下一步；管理看板“订单准备”页签使用该接口。
- 总览中的订单链接使用 `/orders?orderId=:id&view=readiness` 精确打开订单详情“生产准备”页签。详情并行读取单订单检查和处理方案，展示完整六步依据、问题、实时缺料、负责人和依赖；页签本身只读，写操作继续走订单详情原有确认按钮。
- `GET /api/workbench/action-center` 把订单准备、经营风险、数据质量、规则学习和知识库健康合并为统一“今日待办”，按优先级给出建议动作和业务页面入口；看板与 AI 共用该只读结果。当前按单人管理助理设计，不要求分配负责人。V7.1 记录生命周期，V7.2 生成最多 3 项可解释的今日执行队列，V7.3 提供最短处理路径和完成标准，V7.4 在核心业务写入成功后自动复查并汇总最近 24 小时已解决、仍待处理、暂时受阻和反复出现的事项。只有现有订单安全动作能交给 AI 发起确认，查看过程仍不写库。
- `GET /api/workbench/action-history` 只读查询管理事项生命周期；消失表示当前实时检查不再检出，不等同于系统自动判断“人工已经处理完成”。
- `POST /api/workbench/execution-plan` 是 V8.1 的只读统一计划入口，把订单准备、报价转订单或当前管理待办拆成有依赖的步骤。返回结果区分自动核对、业务判断、需确认、页面处理、等待和阻塞；只有 `canExecute=true` 且带确认参数的步骤才已有安全执行器，其他步骤不会由 AI 越权执行。
- 订单详情会把当前订单 ID 和页签作为独立页面上下文交给右侧 AI，用户可直接询问“这个订单为什么不能生产”或“下一步怎么处理”。上下文不写入会话消息，后端会忽略客户端业务数值并重新调用实时工具。
- 订单“客户要求”页签统一管理原始文件和归纳结果。附件旁的“AI 归纳”直接调用 AI 并把结果填入当前编辑框，不跳转工作台或要求复制粘贴；用户核对后再保存草稿，正式知识仍必须在订单页面点击“确认进入知识库”。重新编辑不会覆盖上次确认版，撤销确认只移除知识版本，原文件和草稿继续保留。
- `GET /api/orders/:id/readiness-plan` 把检查结果转换成有顺序和前置依赖的处理方案；区分 AI 可发起确认、人工补资料、业务决定和采购等待，但不直接执行订单或库存写入。按客户名或合同号解析订单使用只读 `/api/orders/lookup`，不会触发采购计划刷新。
- `POST /api/orders/:id/readiness-actions/:actionId` 只执行实时方案中仍为 `confirmable + available` 的白名单步骤。当前支持确认订单和生成采购清单，执行前重新检查，过期或受阻步骤返回 `409`，成功后返回更新订单和新方案。
- 采购中心按供应商和型号聚合数量进度，可批量整项下单；采购中心本身不执行到货或入库。
- 订单保存产品、数量、单位成本、售价、采购清单和待办快照。
- 采购清单中普通零件按 `partId` 或“型号 + 供应商”汇总，线圈转子按正式方案 `coilId` 汇总，并在全部活动订单间顺序分配当前库存。线圈不进入零件库：精确正式方案按套进入 `coils.stock`，没有正式方案的插值/外推线圈标记为非库存计算项。
- “外包装估算”只允许作为报价或成本预估占位项，不进入正式采购清单；订单确认前必须选择零件库中的具体外包装型号和供应商，未解决时准备度返回数据阻塞。
- 配方详情只通过 `GET /api/recipes/:id/inventory-status` 展示配件与线圈当前库存和状态；线圈转子读取独立线圈库存，不提供生产或自动扣库存操作。
- 当前订单状态：`待确认`、`待采购`、`采购中`、`采购完成`、`已关闭`、`已取消`。旧“已完成”数据迁移为“已关闭”。

## 3. 成本口径

完整成本目标口径：

```text
配件 + 线圈 + 动态配置 + 人工工资 + 包装材料 + 管理费
```

### 配件价格

1. 模板手动价或明确快照价优先；
2. 型号和供应商精确匹配；
3. 没有精确供应商时，回退到同型号最低价；
4. 线圈、电容等非普通零件可使用保存的快照价格；
5. 没有任何匹配时按 0 计入，并返回缺失型号。

### 线圈成本

```text
线圈记录单片价 × 片数 + 铜重 × 当前铜价 + 绕线加工费 + 转子加工费
```

- 有精确片数正式方案时使用该记录；无精确片数时只在同一定子组合的正式方案间插值。
- 匹配不跨标准直径、材质或槽眼，测试/停用方案不参与正式成本。
- `12` 是 `120mm` 的俗称；两者按同一标准直径匹配。
- 线圈页提供实时市场指标、同定子组合自动带入和组合批量改单价；成本始终使用线圈记录自身的单片价。
- 铜价每天 15:00 BJT 自动检查，仅在基数或计算成本变化时刷新线圈；铝线价格基数和美元汇率可在市场指标中手动同步。

### 电缆与包装

- 浮球铜套类型为 `standard` 或 `xinjie`；新界式成本在基础浮球价上增加全局 `float_accessory_delta`。
- 电缆成本：`线缆单价 × 长度 + 铜套费`。
- 铜套类型为 `standard` 或 `xinjie`，名称和价格统一存于 `system_settings.cable_accessories`。
- 旧零件备注中的铜套 JSON 仅用于历史数据迁移和回退。
- 包装按配方配置，支持 `standalone`（独立包装）和 `grouped`（组合包装）两种业务方式；材料明细存于 `packingPartsJson`，每项包含型号、供应商、数量、包材类型和 `packingRole`。角色分为 `container`（纸箱/木箱）、`foam`（泡沫）、`pearlCotton`（珍珠棉）和 `fixed`（说明书、贴纸等固定包材）；旧数据由型号与包材类型自动识别，旧 `boxType` 只作为兼容回退。
- 零件库一级分类仍统一使用“包装”，通过 `subcategory` 区分外包装、内衬和固定包材。历史包装零件在启动时按型号、备注及供应商幂等补齐二级分类，不改变价格、库存和供应商。

### 工资与管理费

- 安装、打包、喷漆默认值来自泵壳模板，配方可以覆盖。
- 表面处理成本按配方选择的处理方式计入。
- 管理费优先使用配方值；未设置时回退到全局 `management_fee`。

### 成本接口如何选择

成本展示分三类，不能混用：

- 保存成本快照：配方保存时锁定的成本，用于查看历史配方和订单来源。
- 当日完整成本：按今天的零件、线圈、铜价等基础数据重算 BOM，并叠加安装、打包、表面处理和管理费；配方列表与详情页统一使用这一口径。
- 订单锁定成本：订单创建时写入订单明细，后续基础价格变化不应反向改写历史订单。

| 场景 | 接口 | 说明 |
|---|---|---|
| 应用常用配置 | `POST /api/recipes/model-variant-draft` | 根据常用配置和关联泵壳模板生成配方表单草稿；不写库 |
| 新增线圈同规格带入 | `POST /api/coils/spec-draft` | 根据规格和材质生成录入草稿，统一带入同规格的线重、铜价基数、加工费、默认搭配电缆线径和电容；不写库 |
| 前端单次配件计算 | `POST /api/cost/parts` | Web 当前主入口，只计算传入配件 |
| 配方保存成本快照 | `POST /api/recipes/cost-draft` | 新建/编辑配方保存前生成 `savedTotalCost`、`savedCostDetails` 和标准化配件，并应用长螺丝长度、参数化计价及成品电缆合并规则；不写库 |
| 配方保存 payload | `POST /api/recipes/save-payload-draft` | 保存前检查完整 BOM 不含零价格项目，并统一序列化 JSON、数字、ID、表面处理和技术参数；不写库 |
| 配方当前配件价 | `GET /api/recipes/:id/cost` | 只重算 `partsJson` 的当前配件参考价；不是保存成本，也不保证包含完整人工/管理费 |
| 配方当日完整成本 | `GET /api/recipes/current-costs` | 批量按当前零件价格和当前铜价重算配方 BOM，再叠加人工、表面处理和管理费；用于配方列表展示当日成本及其与保存成本的差额 |
| 报价覆盖试算 | `POST /api/recipes/:id/cost-preview` | 以配方快照为基线，重算被覆盖的动态项 |
| AI/N8N 组合估算 | `POST /api/cost/full-estimate` | 分别叠加配方配件、线圈和动态配置 |

`full-estimate` 的基础配方若已经包含相同线圈或动态项，不应再次传入，否则会重复计价。后端权威成本入口为 `api/services/costEngine.cjs`，前端不再保留独立成本计算口径。

## 4. API 与鉴权

### 请求与响应

- Web 请求统一使用 `apps/web-next/lib/api.ts` 中的 `proxyRequest()`、`proxyFetch()` 或 `proxyStreamFetch()`。
- Web 新调用必须使用当前标准 API 入口；历史字段兼容只允许封装在 API client 内，不得继续扩散到页面组件。
- 前后端字段使用 camelCase；数据库列使用 snake_case。
- 标准成功响应：`{ "success": true, "data": {} }`。
- 标准失败响应：`{ "success": false, "error": "错误信息" }`。
- 核心资源标准输出 `id`、`createdAt`、`updatedAt`。
- `Id`、`CreatedAt`、`UpdatedAt` 是现存历史命名，仅作为临时兼容字段保留，新字段不得继续仿照。

### 鉴权边界

- 公开：`POST /api/auth/login`、`GET /api/auth/check`、`GET /api/health`。
- 常规接口：JWT Cookie。
- 内部服务：`x-internal-secret`，服务端必须配置 `INTERNAL_SECRET`。
- AI、System Prompt、语音：JWT Cookie 或内部 Secret。
- Siri：`x-siri-token`；生产环境必须配置 `SIRI_API_TOKEN`。
- 登录限流：每个 IP 每分钟最多 5 次。

### 核心接口

完整方法、入参和返回见 [API 接口总表](./api-reference.md)。

## 5. 数据安全与自动任务

- 所有动态 UPDATE 必须走 `safeUpdate()`：表名白名单、列名校验、参数化 SQL、更新时间和审计日志。
- 正式业务资源 INSERT 必须走 `safeInsert()`：表名白名单、列名校验、参数化 SQL和审计日志。
- 订单、配方、零件、客户、报价和型号变体使用软删除。
- 线圈、模板和转子历史没有软删除列，使用 `hardDelete()` 并记录审计。
- 系统初始化、`system_settings` / `config` 的 UPSERT 仍是基础设施边界；新增业务资源表不得绕过 `safeInsert()`。
- 零件索引缓存 10 秒；零件变更后必须主动失效。
- 前端增删改后必须重新拉取对应资源，避免只改本地派生状态。
- SQLite 使用 WAL；启动时执行 `wal_checkpoint(TRUNCATE)`。
- 最终表结构以 `api/database/schema.cjs` 为唯一权威来源；版本化迁移、校验和和历史库升级规则见 [`database-schema.md`](database-schema.md)。
- 数据库启动时立即备份，此后每天 03:00 BJT 备份，保留最近 7 份。
- 审计日志在成功备份后清理超过 365 天的记录，可通过 `AUDIT_RETENTION_DAYS` 调整，设为 `0` 禁用。
- 铜价启动时立即检查，此后每天 15:00 BJT 检查；数值未变化时不重写线圈，也不新增审计日志。
- 铝线价格基数和美元汇率可通过市场指标同步接口手动写入系统设置；当前定时任务只自动同步铜价。

## 6. 转子出图

```text
POST /api/rotor/draw 或 /chat
  -> 返回 jobId
  -> GET /api/rotor/status/:jobId 轮询
  -> 成功后下载 fileUrl 或 POST /api/rotor/print/:jobId

POST /api/rotor/save
  -> 保存暂定参数到 rotor_drawings(status=saved)
```

- `/draw` 接收结构化参数，至少提供一项；缺失参数可以由泵壳模板补全。
- `/template-draft` 根据泵壳模板和可选型号变体生成出图表单草稿，不写库；用于统一带入轴承、油封、泵壳 notes 默认参数、不锈钢机筒开档和图纸备注。
- `/save` 接收同一套结构化参数，仅保存到历史，不启动 FreeCAD。
- `/chat` 接收自然语言，可能返回 `need_params` 或安全警告；确认后再出图。
- `/draw`、`/save` 和 `/chat` 可接收 `drawingName` 作为图纸名称，写入 `rotor_drawings.drawing_name`；前端下载 PDF 时用该名称作为文件名。
- `/draw`、`/save` 和 `/chat` 可接收 `drawingText` / `drawing_text` 作为图纸显示文字，生成 PDF 时写入转子图纸底部区域。
- `GET /api/rotor/history` 历史列表标准输出 camelCase 字段，包括 `jobId`、`drawingName`、`fcParamsJson`、`fileUrl`、`linkedPumpModel`、`createdAt`。
- `PATCH /api/rotor/history/:id/name` 用于重命名历史图纸，请求体 `{ "drawingName": "..." }`，成功返回 `{ "success": true, "data": { "drawingName": "..." } }`。
- 转子出图工作台只从泵壳模板带入参数，不再显示或加载型号变体；出图历史在 Web 端可关联订单型号或配方，保存时仍写入 `linked_pump_model` 文本字段。后端旧变体参数只保留历史兼容。
- FreeCAD 默认最多同时执行 2 个任务。
- 图纸和状态写入 `rotor_drawings`，PDF 位于 `public/drawings/`。
- 删除历史记录时同时删除对应 PDF。
- 常用轴承输入如 `201/6201`、`202/6202`、`203/6203` 会自动标准化。

## 7. AI 与移动端

- AI 只允许执行 `tools.cjs` 中已注册的工具。
- 写操作还必须位于 `WRITE_TOOLS` 白名单，并通过确认流程；查询工具不能借机写库。
- AI 调度器 V1 将普通工具结果作为模型继续推理的上下文，不再把查询结果卡片作为对话终点；只有写操作确认会中断等待用户确认。
- Web AI 对话使用 SSE 流式返回内容，并在工具执行前发送执行计划，标明每一步是只读/试算还是需要确认的写操作。
- 报价、订单和配方自动化优先使用草稿/预览工具：`build_recipe_bom_draft`、`preview_recipe_cost`、`preview_pump_shell_cost`、`build_quotation_draft`、`build_order_draft`、`search_customer_history`。这些工具只调用标准业务 API 生成草稿或查询历史，不直接写库。
- AI 询问泵壳本体成本且带有机筒长度/高度时，必须调用 `preview_pump_shell_cost`；该工具会复用 `/api/recipes/bom-draft`，让不锈钢机筒长度加价直接反映到泵壳套件成本。
- AI 可调用 `explain_cost_change` 解释两个配方的成本差异，也可调用 `get_data_quality_summary`、`analyze_recipe_configuration` 和 `get_business_alerts` 读取基础资料健康度、配方配置风险、报价和订单经营异常；这些工具均为只读工具。对配方检查结果可通过 `set_recipe_analysis_feedback` 保存“确认问题、忽略、特殊情况、恢复复核”判断，该写操作必须经用户确认。
- AI 可调用 `check_order_readiness` 检查某个订单当前能否生产。工具返回六步检查过程、实时缺料、采购阶段、阻塞原因和建议入口；它只读标准订单 API，不会自动确认订单、补采购或调整库存。
- AI 可调用 `get_order_readiness_overview` 回答哪些订单不能生产、多少订单缺料或全部订单准备情况。该工具读取实时总览，先返回分类数量，再列出重点订单、主要问题和下一步，不属于写工具。
- AI 可调用 `plan_order_readiness_actions` 把检查问题整理成处理方案。每一步包含顺序、负责人、完成标准、前置步骤和执行方式；`confirmable` 仅表示后续可以由 AI 发起确认，本轮不会自动执行。
- AI 可在用户明确要求执行方案步骤时调用 `execute_order_readiness_action`。该工具属于 `WRITE_TOOLS`，先显示确认卡片；确认后仅调用订单标准动作 API，由服务端实时重验步骤，不能执行人工、等待、需补充输入或已阻塞步骤。
- AI 可调用 `search_factory_knowledge` 和 `get_factory_knowledge_detail` 检索本地工厂知识库；查询 `12-220` 这类线圈键会按材质和槽眼返回全部匹配方案。`sync_factory_knowledge` 会增量更新 `knowledge_entries` 并刷新 FTS，属于需确认的写工具。
- AI 询问价格、成本、库存、订单状态、报价金额和铜价等易变数据时，首轮必须重新调用只读工具，不能直接复述同一会话中的旧数字；明确查询知识库时读取同步后的知识条目，实时业务值冲突时以业务系统当前值为准并提示重新同步。
- AI 知识回答在正文下方提供可追溯的“回答依据与处理过程”，普通回答默认折叠，需要时可展开查看工具计划、调用结果和知识来源；待确认写操作或执行失败会自动展开，避免遗漏必须处理的事项。来源随会话消息一同保存，历史会话也能回看。知识来源可以打开知识详情或原业务页面；待同步条目会显示警告。普通价格、库存、订单和成本查询标记为“实时业务数据”，与“知识库快照”明确区分。
- AI 工作台会把会话和消息保存到 SQLite，支持查看、继续和删除历史会话；上下文仍只发送最近 10 条消息，历史存档数量不受上下文窗口影响。
- 已保存的 AI 回复支持标记“准确”或报告“内容错误、来源过期、资料不足”。反馈会保存当时的问答和知识来源快照，问题进入管理看板“知识库”的待处理队列；它用于人工复核和改进，不会自动改写知识条目、业务数据或业务规则。
- 待处理反馈支持只读诊断和重新验证。诊断会检查原回答引用的知识是否待同步，无引用时搜索可能遗漏的知识，并区分“知识待同步、缺少引用、知识缺口、需业务复核”；重新验证会使用原问题重新查询当前数据，保存新回答和新来源供并排对比，最终仍由人工确认归档。
- 知识库管理中心提供一键回归检查。系统内置项目关键问题，依次重新调用标准 AI 工具链，再用确定性规则核对当前数据库值、调用工具、来源、必需词和禁用词；结果简化为“通过、需要修复、需要确认”，详细回答和失败原因默认折叠。AI 不负责给自己打分。
- Web/PWA 普通工具结果默认弱展示，详细 JSON 折叠；AI 回复必须消化工具结果后给出关键结论、差异原因和下一步建议。
- 订单采购中的成品电缆按“根”汇总，一根由指定长度的线材和对应插头/规格组成；例如 30 台水泵使用 8m 新界式电缆时，采购计划显示 `30 根`，底层线材库存入库时再折算为 `240m`，不得把米数显示成成品电缆数量。
- iPhone PWA 与桌面统一使用 `/ai`；手机端隐藏全局业务导航，使用全屏对话、会话历史抽屉和安全区输入框。
- `/voice` 页面已弃用并兼容跳转到 `/ai`；旧基础语音助手不再作为产品入口。
- PWA 状态流使用单一状态枚举：`idle`、`thinking`、`calling`、`answering`、`confirming`、`done`、`error`、`cancelled`，顶部状态和消息状态都由该状态驱动。
- PWA 当前优先接入成熟 AI 工具：经营概况、最近订单、订单详情、配方成本、零件搜索、线圈成本、铜价、配方对比和出图历史；新建订单、修改订单状态、改零件、生成采购清单、配方/零件写操作必须确认后执行。
- PWA 与桌面共享 SQLite AI 会话历史，可跨设备回看和继续；正式写操作审计仍由后端 `safeInsert` / `safeUpdate` / delete helper 处理。
- 微信小程序代码位于 `wechat-miniprogram/`，当前通过 `INTERNAL_SECRET` 兼容认证；真实密钥不得提交到仓库，小程序生产鉴权应迁移到 OpenID 或服务端会话。
- Siri 使用快捷指令文字输入，不经过 ASR；统一调用 `POST /api/siri/chat`，由 AI tools 决定业务动作，Siri 不直接访问库存、BOM、采购等内部 API。
- Siri 返回 `speech` 供朗读，内容保持简短；结构化结果通过 `resultUrl` 查看，结果临时保存在内存中，5 分钟后失效。
- Siri 写操作返回 `confirmation_required`、`confirmationId` 和确认摘要；用户明确确认后再调用 `POST /api/siri/confirm`，后端仍复用现有写工具确认、标准 API 和审计路径。
- Web/PWA AI 对话使用统一 SSE 模型适配层，`/setup` 默认启用智能路由：普通对话、PDF 文字层、Excel/CSV 和文本走 DeepSeek，统一文件库确认的图片原图自动走 Kimi 多模态；也可以强制固定 DeepSeek 或 Kimi。Kimi 请求失败时自动回退 DeepSeek 与本地 OCR，每条 AI 回复显示实际使用的提供商。工作台附件统一保存到 `factory_files` 并随会话历史恢复；文字型 PDF 自动按页解析，Excel/CSV 保留工作表和单元格定位并可生成只读报价映射草稿，图片与扫描 PDF使用本地中英文 OCR。OCR 技术参数只生成带页码/坐标和置信度的候选，不自动写业务数据。Kimi Coding 订阅凭证与开放平台 API Key 不互通，不能用于业务助手。旧 ASR 接口仅保留兼容，不再由当前工作台调用。

### PWA 调试与限制

- 本地调试：同时启动 Express `:3002` 和 Next `:3000`，访问 `/ai`。
- iPhone 主屏幕安装需要 Safari 和 HTTPS 生产地址；本地 HTTP 可用于页面调试，但不能完整验证主屏幕体验。
- `/voice` 仅保留到 `/ai` 的兼容跳转；当前移动端不请求麦克风权限。

- `apps/web-next/` 是 Next.js + Tailwind + motion 风格的唯一 Web 前端，默认业务入口跑在 `:3000`，并行预览入口跑在 `:3001`，通过 rewrites 将 `/api/*` 代理到现有 Express `:3002`。Next 前端不接管业务 API。
- 数据质量已融合到 `/dashboard` 的“数据质量”视图，读取 `/api/quality/summary`；旧 `/quality` 自动跳转到该视图。报价页和订单页继续通过 `/api/quality/business-alerts` 展示经营异常提醒。
- Knowledge Base V1 使用 SQLite `knowledge_entries` 和可选 FTS5，把零件、模板、配方、线圈、客户、报价、订单、质量问题和业务规则同步成 AI 可检索知识条目；业务页 AI 助手头部提供带二次确认的同步按钮，同步保留稳定条目 ID，并在同一事务内刷新 FTS，不依赖外部向量库。
- Knowledge Base V2 第一阶段在 V1 事实检索之上增加配方智能检查。配方编辑页可手动检查当前未保存 BOM 草稿，点击保存时也会自动检查；系统按模板、BOM 角色、具体型号和线圈配置寻找相似配方，区分“已批准工厂规则”“配置字段与 BOM 的确定性矛盾”和“同类配方高频项复核建议”，并对可比固定件给出带来源的价格提醒。高置信度问题会在落库前要求返回修改或明确确认后继续，普通复核建议不阻止保存；动态泵壳、线圈、浮球、成品电缆和公式项不会套用普通零件价格规则。
- 候选规则经人工批准后立即参与相同泵壳模板的配方检查，并自动更新对应规则知识供 AI 检索。规则提醒会显示批准记录和证据配方，客户定制差异可标记为特殊情况，系统不会自动添加零件或修改成本。
- Knowledge Base V2 第二阶段增加候选业务规则审核。系统只从人工明确确认的同类高频项中学习，按泵壳模板和提醒键归纳，至少需要两个不同配方作为证据；价格提醒和确定性程序错误不会生成候选规则。候选项在看板“数据质量”中批准或驳回，系统不会自动批准或自动修改配方。
- Knowledge Base V3 第一阶段把候选规则升级为证据闭环：同时统计确认、特殊情况和忽略反馈，计算规则置信度并保存证据指纹。新反例出现后，已批准规则进入复核队列；确认支持少于两个配方时自动转为失效，避免旧规则继续进入智能检查或知识检索。系统仍不会自动批准规则、修改配方或调整价格。
- Knowledge Base V3 第二阶段增加规则影响分析。批准候选规则前，系统按当前同模板配方的实时 BOM 和反馈自动列出已符合、需要复核、特殊情况及已忽略的配方；管理看板和 AI 使用同一只读结果，批准确认会明确显示影响数量。影响结果不落库，配方改变后重新分析即可刷新。
- Knowledge Base V3 第三阶段增加已批准规则执行监控。管理看板会自动汇总规则问题次数、受影响配方和已记录例外，并列出每条规则当前需要复核的配方；AI 可查询同一份实时结果。监控只读，不改变数据质量分数，也不会批量修改配方。
- Knowledge Base V3 第四阶段取消日常手动归纳步骤。同类高频项的确认、特殊情况、忽略或恢复复核保存后，会在同一数据库事务中自动刷新候选规则、置信度和复审状态；失败时反馈与归纳整体回滚。看板保留“重新核对规则”作为运维兜底，系统仍不会自动批准规则。
- Knowledge Base V3 第五阶段增加规则生命周期追溯。候选生成、证据变化、批准、驳回、失效和重新激活都会保存不可覆盖的事件记录；看板与 AI 可查询变化时间、前后状态、操作者、说明和当时快照。重复核对相同证据不会制造历史噪声，当前版本不提供自动回滚。
- Knowledge Base V3 第六阶段让规则审核与 AI 检索即时一致。批准规则会自动新增或更新对应知识条目，驳回、恢复候选或自动失效会自动移除，已批准规则证据变化也会刷新置信度；规则状态、历史事件和知识更新处于同一事务，失败整体回滚。该机制仅处理规则知识，零件、配方等其他业务知识仍通过原同步按钮更新。
- Knowledge Base V3 第七阶段支持从生命周期记录恢复规则审核状态。恢复只采用历史事件中的候选、批准或驳回状态，当前规则内容、证据和置信度不会被旧快照覆盖；恢复批准仍按当前证据重新校验，至少需要两个不同配方确认。恢复动作会新增历史记录并同步对应规则知识，任一步失败整体回滚，不会修改配方或强制恢复系统判定的失效状态。
- Knowledge Base V3 第八阶段增加规则准入门槛。候选规则必须同时满足至少两个不同配方确认和不低于 65% 的置信度才能批准；看板和 AI 会说明具体阻断原因。已批准规则如果因新反例跌破门槛，会自动撤回批准、移除对应规则知识并回到待审核，置信度恢复后仍需人工重新批准，不会自动修改配方。
- Knowledge Base V3 第九阶段固化反馈证据来源。服务端保存反馈时会记录当时的配方和泵壳模板；配方后来更换模板，旧反馈只作为“范围漂移”历史记录，不计入旧规则支持数，也不会转移为新模板规则。规则因此失去最低支持时会自动失效并移除规则知识，看板和 AI 会提示在当前模板下重新智能检查并确认。
- Knowledge Base V3 第十阶段隔离配方修改后的过期反馈。即使泵壳模板没有变化，只要配方在反馈后被编辑，旧确认、忽略和特殊情况都会保留为“内容过期”历史证据，但不再影响规则置信度，也不能继续压住当前智能检查提醒；用户按当前配方重新确认后才恢复为有效证据。保存存在学习反馈的配方时，系统会自动重算候选规则并同步已批准规则知识，避免配方数据与 AI 知识之间出现刷新延迟。
- Knowledge Base V3 第十一阶段增加学习证据健康检查。系统会扫描全部同类高频项反馈，包括尚未形成候选规则的单条证据，并区分仍有效、内容过期、模板漂移和归档配方；数据质量看板和 AI 会列出需要重新智能检查的配方。该队列只读，不会自动恢复旧反馈、修改配方或批准规则。
- Knowledge Base V3 第十二阶段打通学习证据逐条复核。数据质量看板的每条待复核反馈都可直达对应配方并自动运行一次智能检查；自动动作触发后会从地址中移除，避免刷新重复执行。用户仍需按当前配置重新确认具体提醒，确认后健康队列随有效反馈自然刷新，全程不自动修改配方。
- Knowledge Base V3 第十三阶段补齐待复核任务的处理结论。看板直达时会携带具体反馈 ID，智能检查会自动定位并高亮仍存在的原提醒；如果原提醒在当前配置中已经消失，用户可明确“确认已解决”。服务端只允许处理确实过期或模板漂移的学习反馈，保留原始证据快照并恢复为中性复核状态，再在同一事务内刷新候选规则，避免已解决任务永久滞留。
- Knowledge Base V3 第十四阶段把待复核反馈按配方聚合为处理任务。同一配方的多条内容过期或模板漂移反馈只占看板一行，一次进入配方智能检查后按队列逐条定位，展示当前进度；重新确认或确认已解决后自动切换下一条。系统仍逐条保存人工判断，不批量确认、不自动修改配方。
- Knowledge Base V3 第十五阶段完成待复核工作台收尾。每次重新判断或确认已解决后，页面会展示候选规则刷新结果，包括新生成、重算、失效和撤回批准数量；多条任务可暂时跳过当前项但不改变反馈状态。整组完成后会清除地址中的复核参数，并可返回数据质量看板重新读取最新健康状态。规则学习仍不会自动批准规则或修改配方。
- Knowledge Base V3 收口审核补强两条服务端一致性边界：“确认已解决”会重新执行当前配方智能检查，仍存在同一提醒时拒绝清理；归档带学习反馈的配方会在同一事务内刷新候选规则和规则知识，防止已归档证据继续支持 AI 规则。
- Knowledge Base V4 第一阶段增加核心业务知识自动同步。零件、泵壳模板、配方、技术附件、线圈、定子规格、客户、报价、订单和系统业务规则通过标准写入 helper 变更后，会提交短延迟合并刷新；连续操作只触发一次同步，内容哈希保证只写入真实新增、更新或删除的条目。失败会自动按 1 秒、5 秒、15 秒重试，看板展示等待、运行、正常或异常状态；启动时自动核对一次。人工同步和 AI 确认工具继续保留为全量核对与故障恢复入口，不改变正式业务数据。
- Knowledge Base V4 第二阶段增加同步运行历史与异常追踪。自动、即时和人工同步无论成功或失败都会保存触发来源、尝试次数、耗时、增删改统计、检索模式和错误原因；重试按独立运行记录保留。看板展示最近记录，历史最多保留 200 次，避免运维日志无限增长。
- Knowledge Base V4 第三阶段增加知识同步健康告警。系统只在自动同步关闭、待同步任务超过 60 秒、同步运行超过 120 秒、存在未安排的知识变化或最近同步失败时提示，不会因为长期没有业务数据变化而误报。异常直接显示在知识库看板，可进入现有确认流程执行人工核对和恢复；恢复成功后告警自动消失。
- Knowledge Base V4 第四阶段让 AI 可以只读诊断知识同步健康状态。用户询问知识库是否正常、最近同步是否成功、失败原因或是否需要手动同步时，AI 会实时读取 `/api/knowledge/health`，说明健康级别、待同步数量、异常原因和最近运行记录；诊断本身不会执行同步，人工恢复仍必须经过确认。
- Knowledge Base V5 第一阶段增加独立工厂资料源。管理看板可导入技术说明、文本、Excel、性能测试报告和 PDF 图纸原件，资料通过 `safeInsert/softDelete` 保存并自动生成 `document` 知识条目。文本和 Excel 提取正文进入现有 FTS；PDF 当前只检索标题、说明、标签和文件信息，界面与 AI 都必须明确未解析正文，不得推断图纸技术参数。原文件保存在 SQLite，可从知识详情下载；删除资料会自动移除派生知识。
- Knowledge Base V6.1 增加本地向量存储与模型适配底座。`knowledge_embeddings` 保存按条目和模型唯一的 Float32 向量、维度及内容哈希，`sqlite-vec v0.1.9` 提供精确余弦距离，`multilingual-e5-small` 通过固定版本的本地运行时按需加载。`/api/knowledge/vector-health` 可只读检查扩展、模型缓存和覆盖率；当前检索仍使用 FTS，不会在 API 启动时下载模型，组件不可用也不会阻塞现有知识搜索。
- Knowledge Base V6.2 增加后台增量向量同步。文字知识事务成功后按内容哈希分批生成新增或变化向量，来源删除立即级联清理；模型或维度切换支持断点续跑，全部新向量完成后才清理旧模型。模型、批次或运行历史失败都不回滚业务数据和 FTS，系统自动重试并通过 `/api/knowledge/vector-health`、`/api/knowledge/vector-sync-runs` 暴露覆盖率、队列状态和持久化统计。当前搜索仍使用 FTS，混合检索留在 V6.3。
- Knowledge Base V6.3 启用 FTS/BM25 + 本地向量混合检索。稳定 RRF 融合保留两路候选，型号、规格、客户名、合同号等精确命中优先；结果附带命中方式、关键词名次、向量距离和最终分数。类型和来源过滤在两路保持一致，查询模型或扩展异常时自动返回原 FTS/LIKE 结果，AI 工具入口不变。
- Knowledge Base V6.4 增加纯本地检索评测和上线验收。固定中文问题覆盖型号、口语、错别字、配方、线圈、成品电缆、成本、报价和测试报告别名，自动比较 FTS、纯向量和混合 Top 1/Top 3；SQLite 在线备份恢复会核对完整性、外键、向量数量及真实余弦查询。知识库看板展示向量覆盖率、混合/回退模式、待生成和模型异常，不要求日常人工同步。
- V8.1 增加统一工厂执行计划。AI 工具 `plan_factory_workflow` 可以规划订单生产准备、报价转订单和当前管理待办，统一展示目标、业务对象、步骤依赖、完成标准和执行保护。计划工具只读；订单已有安全动作继续先确认再执行，报价转订单当前仍从报价页面使用原有预览、确认和事务接口。
- V8.2 打通首条跨模块安全执行链。已接受且资料完整的报价会在计划中返回受保护的 `execute_factory_workflow_step`；用户确认后，AI 重新检查实时计划、生成订单草稿预检、复用原事务转单接口，并自动读取新订单生产准备方案和原报价完成状态。未确认、计划过期、报价状态变化、重复转单或预检失败都不会产生订单。
- V8.3 在统一执行计划中提供高频操作捷径。计划顶部可精确进入当前报价、订单或管理待办，步骤可直接进入携带业务 ID 和页签的处理页面；报价链接会自动打开对应报价详情。只有当前计划标记为 `available + confirmable + canExecute` 且确认器属于现有白名单的步骤才显示“发起确认”。点击后只是向 AI 发送重新检查请求，仍需生成最新计划并展示原确认卡片，历史会话不提供执行捷径，也不会从前端直接调用写接口。
- V8.4 增加执行历史和恢复保护。订单安全动作与报价转订单每次确认尝试都会保存计划指纹、成功或失败、结果摘要、错误和最新复查结论；后续计划展示最近尝试，并只允许对当前实时计划中仍未完成、仍可执行的失败步骤重新发起确认。同一计划版本已有成功记录时会清除确认参数并标记完成，业务状态变化时停止直接重试。
- V9.1 增加统一文件对象和 AI 聊天附件。PDF、Excel、CSV、UTF-8 文本和常见图片先经过 10MB 限制、文件名清理、扩展名与真实内容签名核对，再按 SHA-256 保存或复用 `factory_files`；重复上传不会新增二进制对象。知识资料、配方测试报告和 AI 会话附件复用同一文件对象，聊天历史可恢复图片预览和文件下载。模型层支持 `auto/deepseek/kimi`：智能路由以 DeepSeek 为默认模型，仅在真实图片附件需要视觉能力时发送图片二进制给 Kimi。
- V9.2 增加 PDF 文字层和表格解析。标准文件上传自动保存按页文本、行坐标、连续表格行、页数和截断状态，聊天附件可按页进入模型上下文；解析失败保留原件和错误状态，可通过 `/api/files/:id/parse` 重试。V9.4 已接续处理当时标记 `requiresOcr` 的扫描页。
- V9.3 增加 Excel/CSV 通用表格理解和报价文件映射。统一文件保存工作表、行列、单元格引用、公式、表格块和截断状态；AI 使用 `inspect_quotation_file` 对照当前客户与配方生成只读映射草稿，精确命中后才能把候选输入交给现有标准报价草稿 API。近似、多候选和未找到项必须确认，文件单价不覆盖系统成本，也不会自动新增客户、配方或报价。
- V9.4 增加图片与扫描 PDF 本地 OCR。中英文识别模型随项目安装，扫描 PDF 先渲染最多 12 页再识别；结果保留页码、行号、文字框和置信度，并从明确文字中提取直径、尺寸、螺纹、轴承、电气参数等候选。低于 85% 或页面整体低置信度会标记 `needsReview`，任何候选都不会自动写入技术档案。OCR 无文字时保留原件并返回 `metadata_only + ocrApplied=true`，AI 不得推断。
- V9.5 增加统一文件归档关系。`factory_file_links` 把同一原文件关联到客户、报价、配方、配方检查问题、AI 回答问题或知识资料，不复制二进制；重复关联自动去重，删除原文件前会检查业务引用。AI 先用只读工具查找真实归档对象，再通过确认卡片写入；聊天附件卡片也可打开归档弹窗并查看已有归档。归档到知识库会创建或复用 `knowledge_documents` 并触发现有自动同步，OCR 候选不会因此变成已确认技术参数。
- V9 文件智能处理已完成收口：聊天可直接上传 PDF、Excel、图片或报价文件，完成当前会话分析后再显式归档；客户详情、报价详情、数据质量页和 AI 回答反馈提供统一附件面板。业务附件关联不等于知识入库，只有明确归档到知识库的资料才会进入长期检索。操作边界和试用路径见 [V9 文件智能处理使用大纲](./v9-user-guide.md)。
- V10.1-V10.4 把客户原始要求、人工确认结论和订单执行事实纳入订单追溯。订单详情“客户要求”负责归纳客户原文，“执行档案”按生产前、生产中、生产后记录资源准备、产能或供应商调整、过程异常、质量与交付结果。V10.4 的只读订单知识包把这些确认事实与实时订单、采购、待办和生产准备状态合并供 AI 查询，并保留来源文件；未确认草稿不会作为事实。整个流程不自动修改订单状态、配方、采购或库存。使用方式见 [V10 使用大纲](./v10-user-guide.md)。
- 向量命中只用于发现可能相关的知识，不等于已经证实业务用途。纯向量结果标记为 `semantic_candidate`；AI 不得据此把相似泵壳、叶片数量或普通 BOM 配件解释成“切割专用”，用途、兼容性和专用配件关系必须有知识标题、摘要、正文或结构化字段的明确文字依据。系统未记录时直接说明无法确认。
- 用户确认的切割业务语义已固化为正式规则知识：`800平刀切割泵壳`明确用于切割杂草；SPA 2叶/3叶是没有切割刀片的清水泵壳；“切边6mm长螺丝”是外六角螺丝而非刀片；`v800平刀-不配刀`不能作为带刀完整方案。是否随 800 平刀泵壳附带刀片在摘要、正文和 metadata 中均标记为未确认，AI 不得自行声称“配有刀片”或“全套含刀”。
- 产品用途、适用型号和专用配件等事实问题每轮强制刷新知识。获得本轮工具结果后，历史 AI 回复会从事实合成上下文中移除，避免旧错误答案反向覆盖新证据；已有明确文本命中时，纯向量候选不再提供给回答模型，只保留在检索层用于没有文本证据时的召回。
- 发布前的 `npm run test:deep-api` 使用 SQLite 在线备份创建系统临时副本，在随机端口验证认证、核心查询、零件/模板/型号/配方、报价转订单、采购进度、线圈库存、AI 会话、知识同步和删除保护；完成后自动检查并清理副本，不修改当前业务数据库。
- 管理看板“知识库”视图用于观察 Knowledge Base 的实际状态，不增加独立导航。该视图提供全文搜索、知识分类、最新/待同步筛选、来源追溯、知识详情和最近同步历史，并通过只读内容哈希比较识别待新增、更新及来源已删除条目。V4 默认在核心业务写入后自动刷新派生知识；人工二次确认同步仍可执行全量核对和故障恢复。
- 管理看板“知识库”同时汇总 AI 回答问题反馈，按内容错误、来源过期和资料不足分类，支持查看原问题、回答、反馈说明及当时引用的知识来源，并提供来源新鲜度诊断、候选知识核对和原问题复测。新旧回答可并排比较，人工填写处理说明后归档；反馈记录与会话按登录身份隔离。
- 管理看板“知识库回归检查”首批覆盖价格更新、线圈多方案、性能测试报告类型、测试模板无效字段、客户报价顺序和成品电缆语义。运行会调用外部 AI，因此不并入普通 `npm test`；页面可一键执行，开发和发布验收使用 `npm run test:knowledge-live` 自动执行并保存每次结果，业务数据库不会被修改。
- 客户历史工具按报价创建时间生成连续展示顺序，AI 只显示“第 1 份、第 2 份”，不把删除后不连续的数据库 ID 当作报价序号。知识库中的报价标题同样不展示内部 ID。
- 配方性能测试报告上传后会解析型号、报告号、日期和逐点性能数据；下一次知识库同步会把逐点流量、扬程、电流和效率等实际曲线数据并入对应配方条目。报告模板中的规定点、实测点和偏差仅保留在原始解析数据中，不进入界面摘要或 AI 检索，避免沿用其他型号模板造成误判。原始 Excel 作为 SQLite BLOB 随数据库一同备份。
- 数据质量中的配方完整性只要求真实零件行能在零件库匹配；`线圈转子` 由线圈模块校验。电缆线材与插头/规格费用统一保存、展示为一条“成品电缆”BOM，采购和库存仍按其中记录的实际米数计算；旧配方中拆开的电缆配件费会在读取时自动合并。
- AI executor 已通过内部 API client 调用标准 API，不再直接访问数据库 helper；后续新增 AI 自动化能力时，应先确认是否能复用现有标准业务动作 API。
- 业务 API 已统一使用 `{ success, data/error }` 响应格式；健康检查等监控入口可保留非业务格式。
- 核心资源响应中仍可能带有 `Id/CreatedAt/UpdatedAt` 历史兼容字段；Web 调用必须使用标准 camelCase。
- 配方等写接口仍保留少量历史入参兼容，但资源更新和删除已统一为 `/:id` 路径入口。
- 历史兼容字段和旧入参只允许停留在后端边界与 API client normalize 层；新增功能不得扩大旧字段使用面，具体约束见 [API 开发 SOP](./api-sop.md)。
- 关键写接口的路由 ID、成本基础资料数字字段、模板/变体 JSON 字段，以及订单/报价/配方保存草稿的金额和数量字段已统一走 `api/services/validation.cjs`。
- 审计日志覆盖正式业务资源的 INSERT、动态 UPDATE 和 DELETE；系统初始化与 settings/config UPSERT 仍属于基础设施边界。
- `GET /api/recipes/:id/cost` 不是完整配方总成本接口，报价应使用 `cost-preview`。

这些属于历史兼容边界，不应成为新代码继续扩散兼容写法的理由。
