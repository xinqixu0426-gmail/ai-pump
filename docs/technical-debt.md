# 当前技术债与优化清单

> 更新于 2026-08-27。
>
> 本文只保留尚未完成、会影响正确性、维护成本或下一阶段演进的事项。已经完成或失效的整改过程由 Git 历史保存，不继续留在当前文档中。

## 1. 当前结论

2026-08-03 CTO 代码审核综合评分为 **87/100**。系统已经具备可靠的模块化单体、正式成本权威、Command/Query 分层、持久幂等、资源版本、事务、强审计和自动化发布门禁。

当前不需要继续为了架构形式拆后端 service。优化重点按顺序是：

1. 补齐新增能力的真实 API 和页面回归；
2. 渐进拆分前端巨型组件，降低修改耦合；
3. 在出现多人协作需求时升级身份与权限模型。

## 2. P2：测试与发布可信度

### 2.1 供应商小套件补齐完整业务链测试

当前已有 Command 归一化、BOM 引擎单元测试，以及 HTTP 创建/读取中的正数数量、未知字段忽略回归；尚未完整覆盖：

- HTTP 修改和重新编辑回填；
- 父型号不存在、组成项超限和并发版本冲突；
- 页面保存、关闭、重新打开和再次保存；
- 窄屏下组成项编辑、删除、错误提示和未保存保护；
- 小套件父项在配方、报价、订单和库存状态中的一致展示。

完成标准：

- 聚焦单元测试通过；
- `npm run verify:api-contract`、`npm test`、`npm run test:deep-api` 和 `npm run build` 通过；
- 至少完成一次真实浏览器桌面和移动端回归，并记录结果。

### 2.2 历史命名兼容退役

当前 Web 业务模型统一使用 `id/createdAt/updatedAt`；零件说明统一为 `remark`，零件目录成本在页面模型中统一为 `catalogUnitCost`。数据库字段、`/api/model-variants`、`modelVariantId/modelName`、capability ID 和部署路径仍是稳定技术标识，不因界面术语调整而改名。

为避免破坏已有 AI、MCP 和外部调用，后端 Row Adapter 暂时保留 `Id/CreatedAt/UpdatedAt`，零件接口暂时保留 `notes` 兼容字段。它们只允许出现在明确的适配器、规范化器和兼容测试中，不得重新进入页面状态或新调用代码。

退役旧别名前必须同时满足：

- 完成仓库内调用方盘点，并确认页面和正式客户端只使用规范字段；
- 结合外部调用和 MCP 运行记录确认兼容字段已无实际消费者；
- 在 `api-reference.md` 标记废弃窗口，并提供至少一个兼容周期；
- 删除旧字段后，API 契约、深层 API、AI/MCP 与完整 Web 构建全部通过。

这项债务不授权直接修改数据库列、公开路径或 capability ID；若确需迁移，必须作为独立 API 兼容任务实施。

## 3. P1：巨型组件瘦身

### 3.1 是否需要瘦身

**需要，但应渐进拆分，禁止一次性重写。**

当前主要巨型组件：

| 文件 | 当前规模 | 主要耦合 |
|---|---:|---|
| `apps/web-next/components/recipes-view.tsx` | 2,436 行 | 配方列表、草稿编排、模板入口、就地建档、成本/BOM 预览和多类弹层 |
| `apps/web-next/components/quotations-view.tsx` | 1,736 行 | 报价列表、编辑、成本覆盖、包装配置和转单 |
| `apps/web-next/components/knowledge-view.tsx` | 1,584 行 | 知识资料、回归评测、反馈处理、向量健康和详情弹层 |
| `apps/web-next/components/ai-view.tsx` | 825 行 | 页面级编排、对话发送、工具结果回写、工厂配置与知识同步；独立展示和局部状态已拆出 |

问题不只是行数，而是一个文件同时承担多个独立变化原因：

- 任一小功能都需要理解整个工作台状态；
- `useEffect/useMemo` 依赖容易形成陈旧闭包或漏刷新；
- 桌面与移动布局在同一渲染树中重复；
- 冲突集中，代码审核难以判断改动是否越界；
- 单元测试只能覆盖 helper，真实交互回归成本持续上升。

### 3.2 瘦身原则

- 以业务职责和状态所有权拆分，不按视觉碎片机械拆小组件；
- 页面容器只保留资源加载、当前工作区选择和跨区协调；
- 表单草稿只能有一个所有者，子组件通过明确 props 和事件修改；
- API 调用继续集中在 `apps/web-next/lib/*`，不得搬进展示组件；
- BOM、成本、库存、状态机和校验权威仍在后端，不以“拆组件”为由复制到前端；
- 每次只迁移一个稳定边界，迁移前后保持 API、文案、键盘操作和移动端行为一致。

规模是预警指标，不作为机械考核：

- 超过约 1,500 行或同时承担 3 个以上独立业务域时，应进入拆分评估；
- 超过约 2,500 行时，不应继续直接叠加大型功能，新增能力应优先抽出稳定边界；
- 新提取的业务区块通常控制在 300～800 行；复杂区块可以更大，但必须保持单一状态责任。

### 3.3 推荐顺序

#### 第一批：`ai-view.tsx`

建议拆出：

- 会话列表与当前会话；
- 消息渲染和工具证据；
- 流式请求状态；
- 写操作确认卡片；
- 附件区；
- 回答反馈、文件归档和知识同步弹层。

写操作确认状态必须继续由服务端 token 和正式回执驱动，不能因组件拆分退化为前端布尔值。

当前进度（第一阶段已结束）：

- 第一批已完成：文件归档、回答反馈、会话删除、知识同步和工厂配置五类弹层迁入 `components/ai/AiWorkspaceDialogs.tsx`；
- API 调用、保存状态和结果刷新仍由 `ai-view.tsx` 持有，展示组件不直接请求接口；
- 第二批已完成：回答依据与确认卡片迁入 `AiAnswerProcess.tsx`，通用结果展示迁入 `AiBusinessResult.tsx`，执行计划展示迁入 `AiWorkflowResults.tsx`，格式化和表格基础迁入 `AiResultPrimitives.tsx`；
- 写操作确认仍使用服务端签发的确认 token，执行计划展示不自行构造业务事实或直接写入；
- 第三批已完成：桌面与移动会话侧栏迁入 `AiConversationSidebars.tsx`，会话加载、打开、删除和搜索状态迁入 `useAiConversationHistory.ts`，流式事件归并、终止控制和消息上下文迁入 `useAiMessageStream.ts`；
- 会话展示组件不直接请求接口；历史状态 Hook 只调用统一 `lib/ai.ts` 客户端，流式状态 Hook 不承载业务事实或写确认；
- 第四批已完成：附件能力读取、上传和临时文件清理迁入 `useAiAttachments.ts`，消息附件与待发送预览迁入 `AiAttachmentDisplays.tsx`，归档查询和保存状态迁入 `AiAttachmentArchiveController.tsx`；
- 临时附件仅在会话消息保存成功后转为持久关联，上传失败和主动丢弃仍清理未引用文件；归档控制器继续通过 `lib/files.ts` 调用正式 API；
- 第五批已完成：消息区迁入 `AiMessageList.tsx`，输入区迁入 `AiComposer.tsx`，语音识别生命周期迁入 `useAiSpeechInput.ts`，回答反馈状态与保存迁入 `useAiAnswerFeedback.ts`；
- `ai-view.tsx` 已由最初 3,409 行降至 825 行；后续新增编排使规模较第一阶段收口时回升，当前仍只保留页面级跨模块协调、标准对话发送、工具结果回写、工厂配置和知识同步；
- 第一阶段到此结束。后续不得仅为降低行数继续机械拆分；只有出现新的独立变化原因、明显状态耦合或测试边界时，才启动第二阶段。

#### 第二批：`recipes-view.tsx`、`quotations-view.tsx` 与 `knowledge-view.tsx`

状态：**可选优化，暂缓实施。**

这三个工作台目前没有已确认的正确性阻塞，继续瘦身的收益主要是降低后续维护成本，不是当前发布前置条件。只有在新增功能明显扩大状态耦合、同一区域频繁产生回归，或单次修改需要跨越多个独立业务区时再恢复：

- `recipes-view.tsx` 按资源加载、草稿编排、模板/目录协调和弹层状态拆分；
- `knowledge-view.tsx` 按资料、评测、反馈治理和运行健康拆分；
- `quotations-view.tsx` 按列表、编辑草稿、成本覆盖和转单流程拆分。

恢复时一次只推进一个工作台，避免并行重构扩大回归面。

### 3.4 瘦身验收标准

- 功能、API、业务结果和当前用户路径不改变；
- 写操作后仍重新拉取对应资源；
- 没有新增裸 `fetch()`、前端成本公式或 snake_case 类型；
- 现有 lint warning 不增加，迁移区的 Hook 依赖 warning 应清零；
- 聚焦测试、全量测试和生产构建通过；
- 桌面、窄屏、键盘操作、弹层滚动和未保存保护完成真实页面回归；
- 拆分后顶层文件只承担编排，不再直接包含全部业务区块实现。

## 4. 条件触发项：身份与权限

当前共享密码和单一 `admin` 角色适合单工厂、少用户的内部系统，不作为当前阻塞项。

出现以下任一条件时，身份与权限升级为 P1：

- 多名员工需要区分报价、采购、库存、技术和管理员权限；
- 需要追溯到具体操作者而不是会话；
- 系统对外提供给其他工厂或远程协作方；
- 需要撤销单个用户权限而不轮换全局密码。

届时应引入独立用户身份、密码哈希、会话撤销、领域权限和操作者审计；不能只增加前端菜单隐藏。
