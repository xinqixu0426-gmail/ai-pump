### 2.2 历史命名兼容退役

当前 Web 业务模型统一使用 `id/createdAt/updatedAt`；零件说明统一为 `remark`，零件目录成本在页面模型中统一为 `catalogUnitCost`。数据库字段、`/api/model-variants`、`modelVariantId/modelName`、capability ID 和部署路径仍是稳定技术标识，不因界面术语调整而改名。

为避免破坏已有 AI、MCP 和外部调用，后端 Row Adapter 暂时保留 `Id/CreatedAt/UpdatedAt`，零件接口暂时保留 `notes` 兼容字段。它们只允许出现在明确的适配器、规范化器和兼容测试中，不得重新进入页面状态或新调用代码。

退役旧别名前必须同时满足：

- 完成仓库内调用方盘点，并确认页面和正式客户端只使用规范字段；
- 结合外部调用和 MCP 运行记录确认兼容字段已无实际消费者；
- 在 `api-reference.md` 标记废弃窗口，并提供至少一个兼容周期；
- 删除旧字段后，API 契约、深层 API、AI/MCP 与完整 Web 构建全部通过。

这项债务不授权直接修改数据库列、公开路径或 capability ID；若确需迁移，必须作为独立 API 兼容任务实施。

## 3. P1：巨型组件瘦身

### 3.1 是否需要瘦身

**需要，但应渐进拆分，禁止一次性重写。**

当前主要巨型组件：

| 文件 | 当前规模 | 主要耦合 |
|---|---:|---|
| `apps/web-next/components/recipes-view.tsx` | 2,515 行（2026-09-07） | 配方列表、草稿编排、模板入口、就地建档、成本/BOM 预览和多类弹层 |
| `apps/web-next/components/quotations-view.tsx` | 1,731 行（2026-09-07） | 报价列表、编辑、成本覆盖、包装配置和转单 |
| `apps/web-next/components/knowledge-view.tsx` | 1,862 行（2026-09-07） | 知识资料、回归评测、反馈处理、向量健康和详情弹层 |
| `apps/web-next/components/ai-view.tsx` | 866 行（2026-09-07） | 页面级编排、对话发送、工具结果回写、工厂配置与知识同步；独立展示和高频输入状态已拆出 |

问题不只是行数，而是一个文件同时承担多个独立变化原因：

- 任一小功能都需要理解整个工作台状态；
- `useEffect/useMemo` 依赖容易形成陈旧闭包或漏刷新；
- 桌面与移动布局在同一渲染树中重复；
- 冲突集中，代码审核难以判断改动是否越界；
- 单元测试只能覆盖 helper，真实交互回归成本持续上升。

### 3.2 瘦身原则

- 以业务职责和状态所有权拆分，不按视觉碎片机械拆小组件；
- 页面容器只保留资源加载、当前工作区选择和跨区协调；
- 表单草稿只能有一个所有者，子组件通过明确 props 和事件修改；
- API 调用继续集中在 `apps/web-next/lib/*`，不得搬进展示组件；
- BOM、成本、库存、状态机和校验权威仍在后端，不以“拆组件”为由复制到前端；
- 每次只迁移一个稳定边界，迁移前后保持 API、文案、键盘操作和移动端行为一致。

规模是预警指标，不作为机械考核：

- 超过约 1,500 行或同时承担 3 个以上独立业务域时，应进入拆分评估；
- 超过约 2,500 行时，不应继续直接叠加大型功能，新增能力应优先抽出稳定边界；
- 新提取的业务区块通常控制在 300～800 行；复杂区块可以更大，但必须保持单一状态责任。

## 4. 条件触发项：身份与权限

当前共享密码和单一 `admin` 角色适合单工厂、少用户的内部系统，不作为当前阻塞项。

出现以下任一条件时，身份与权限升级为 P1：

- 多名员工需要区分报价、采购、库存、技术和管理员权限；
- 需要追溯到具体操作者而不是会话；
- 系统对外提供给其他工厂或远程协作方；
- 需要撤销单个用户权限而不轮换全局密码。

届时应引入独立用户身份、密码哈希、会话撤销、领域权限和操作者审计；不能只增加前端菜单隐藏。

### 7.1 目标、范围与使用方法

最终用户流程：选择类别、填写实际规格，系统生成标准名称；规范同一物料的叫法后，所有相关业务页面显示新名称，引用、库存、采购进度和已锁定业务事实连续有效。

范围包含零件、泵壳套件、供应商小套件、线圈方案、模板和配方的名称；引用链覆盖新建/编辑/复制/就地建档、BOM、成本、报价、订单、采购、库存、默认配件、搜索、导出、AI/MCP 和关联资料标签。历史常用配置入口仍在时也必须覆盖。

执行顺序固定为：**P0 → P1 → P2 → P3 → P4 → P5 → P6 → P7 → P8**。P0—P7 在开发环境及隔离数据库完成；正式改名与生产切换仅在 P8 进行。每阶段应形成可审查提交，记录实际命令、结果和剩余阻塞。未满足阶段通过条件不得标记完成。

复用现有 SQLite、正式 capability、Preview/Command、幂等、版本检查、事务、强审计、业务变更记录和 API 客户端。开发前完整阅读 [API 契约](api-contract.md)、[API SOP](api-sop.md)，发布和恢复遵循 [备份恢复](database-backup-recovery.md)及[运行手册](operations-runbook.md)。

### 7.3 必须保持的业务不变量

1. **物料身份不随名称改变。** 同一零件使用原 `partId`，线圈使用原 `coilId/schemeCode`；模板、配方保留原 ID。不得删除重建以完成改名。
2. **标准名称只有一个权威来源。** 由后端根据类别规则和结构化规格生成。前端预览、网页保存、AI、MCP、批量导入和就地建档调用同一规则。
3. **名称不是业务条件。** 匹配、成本角色、库存、类别、采购合并和参数推导不再靠名字里的“长螺丝”“线径”等字样判断；迁移期旧字符串解析只留在显式兼容适配层。
4. **规格变化不等于改名。** 5×12 换为 5×20 必须选择/新建另一物料并走明确替换；同一实物资料录错用受控纠错。规格修订与名称修订分开，不能仅删除旧名称校验而放松防错。
5. **当前业务页统一显示现名。** 包括已关闭订单和历史报价的日常查看页；原始快照、修订历史、审计内容、已生成文件原文保持原样，必要时另示“当时名称”。
6. **纯改名不产生业务数量/金额变化。** 库存、预留、用量、已下单/到货/入库数量、实际采购价、锁定成本、销售价、订单状态不变；不因刷新名称重算并保存订单。
7. **供应商与配置边界保留。** 同规格不同供应商继续保留各自物料身份；同一基础电缆的不同长度、接头、单位等保持不同采购配置，不能仅按 `partId` 合并。
8. **用途名称独立。** “提手螺丝”“压板螺丝”等 BOM 角色不跟着物料名改写。小套件只绑定、计价、扣减父物料；非库存费用不强造零件 ID。
9. **读操作无写副作用。** 当前名称装配在内存完成；不在 GET、页面加载、AI 查询中回填 ID、改快照、同步知识或生成审计。
10. **实时刷新保护草稿。** 名称更新不得覆盖未提交的数量、供应商、选配或备注；过期写预览仍按正式协议拒绝并重新预览。

### 7.4 数据与契约设计基线（P1 冻结，以下均为拟新增或拟调整）

采用增量改造，不引入新的 ERP 平台或微服务。优先沿用 `parts.model`、`coils.scheme_name`、`recipes.name` 等现有名称载体；禁止再维护另一份可以独立编辑、与标准名称冲突的显示名。

| 数据职责 | 建议实现 | 约束 |
|---|---|---|
| 命名输入 | 按类别登记且受 schema 校验的规格对象、命名规则版本、命名状态 | 规则版本影响已有名称时走显式预览/迁移，不在读取时静默改名；已有 `remark` 业务元数据保留 |
| 实物规格身份 | 规范化后的关键规格及独立规格修订 | 名称修订不能改变实物规格身份；字段范围在 P1 按类别固定 |
| 标准名称 | 后端生成后存入对象现有名称字段 | 名称冲突时检查规格差别与供应商，不随机追加“副本2” |
| 原厂/对外型号 | 与内部生成名分开记录，报价/订单冻结各自对外型号 | 现有型号中的 V750、TOKOY 等不能未经核实丢弃或认定为客户/品牌 |
| 模板绑定 | 套件模式增加明确泵壳 `partId`；固定配件、组件、默认配件保存类型化引用 | `shellModel` 不再同时承担模板显示名与物料关联键；多供应商不按最低价猜选 |
| 历史名称 | 原单据快照与审计保留当时名称 | 旧称弃用，不搜索、不作为关联键；已有别名表暂不启用，不做破坏性删表 |
| 当前读取结果 | 区分 `currentName`、`snapshotName`、类型化 ID、解析状态及名称版本 | 字段名在能力契约中冻结；旧响应字段语义不得直接从快照偷换为现名 |
| 新业务引用 | JSON/BOM/明细保存正式 `partId/coilId/recipeId/templateId` 与必要的配置身份 | 前端展示优先现名，写入提交 ID 和业务版本，显示字符串不是写目标 |
| 旧快照绑定 | 使用独立、可审计的历史引用绑定记录，关联原对象/版本/JSON 位置/源内容哈希与目标 ID | 保持已锁定 JSON 原文与金额不变；源版本或位置变化时原绑定失效，禁止套用到另一行 |
| 实时通知 | 复用持久业务变更事件及单调游标，通知实体类型/ID/版本 | 无需广播整份订单；名称提交后可立即从正式 Query 读到 |

旧快照绑定属于正式迁移结果；新保存的业务数据直接带正式 ID，不重复维护第二套权威关联。用于“被哪些对象引用”的反向索引可以派生，但必须可重建，不能替代正式引用。

命名示例采用 `品名-规格-必要区别`。分类规则至少覆盖轴承、机械/骨架油封、螺丝、泵壳、泵壳搭配、浮球、电缆、电容、皮垫、配件、包装、线圈、模板及配方。维度内统一 `*`，型号字母大写，片数明确写“片”；物理单位按已核实含义规范化，不把现有“线径0.55”擅自解释成 mm 或 mm²。定子俗称“12”保留与 120mm 的已确认映射。

配方内部识别采用“成品型号＋必要结构/配置区别”，配置摘要由完整规格自动生成；同名异配置必须补充真实区别。采购父物料、模板和最终配置名称分别生成，不能因为共用某泵壳就把不同成品型号合并。

新规则下必填规格缺失阻止正式新建；存量不完整记录显示“待规范化”，仍可按已核实 ID 查询或履行既有业务。非标件通过“品名＋明确规格＋必要区别”结构化入口录入，不能成为任意修改整串标准名称的后门。

### 7.10 当前实现与剩余接入

开发分支为 `codex/spec-naming-live-references`。正式内部只读能力 `catalog.reference_audit` 的入口为 `npm run audit:catalog-references -- [数据库路径]`；实现位于 `api/services/catalogReferenceAudit.cjs`，旧名称候选提取独立位于 `catalogNamingCandidates.cjs`。不加载 `api/db.cjs`，在单个只读事务中扫描声明的数据表、JSON 及二次嵌套字符串，输出引用位置、源哈希、库存/单据基线和候选改名表。供应商套件内部描述不计为独立库存；缺失、停用、歧义、ID/名称不一致与预算超限分别报告。

本地报告保存在被 Git 忽略的 `logs/catalog-naming/`。新增 `costBaseline` 固定目录价、线圈记录及白名单业务设置，复用正式 `costEngine` 计算“保存 BOM 按当前目录价”的配件成本；不是重新展开完整 BOM 的当日整泵成本。采购清单与订单明细原 JSON 一并保留，供核对行 ID、配置、预留输入和采购进度。完整成本入口的迁移前后等价验收仍待执行。`complete` 仅说明声明范围内扫描未失败，不能当作全链条已完成的证明。

命名规则、名称预览和按 ID 批量读取现名已有正式 API，契约见 `api-reference.md` §4.1。版本83通过隔离迁移测试，提供命名档案、别名、历史绑定和模板泵壳绑定的存储；主库仍未运行本次迁移。配方选配/包装预览以及模板固定项/组件已保留明确 ID，参考价按同一 ID 读取；换长度的长螺丝不继承旧规格 ID。名称预览的输入指纹不能替代完整实物指纹，线圈电气参数等正式属性仍需纳入后续保存校验。

历史显示引用已有 `catalog.bind_references` 预览/确认保存和 `catalog.bound_names` 分页读取。只建立经盘点唯一核实的旁路绑定，提交重验来源、目标和档案哈希；legacy 档案不冒充完整实物身份。来源变化明确失效，读取现名不回写历史快照。命令具备显式幂等、强审计、事务回滚及业务事件，尚未作为采购或入库的身份授权依据。

采购计划、总览、单项进度和批量下单已统一使用物料与配置身份；新行生成稳定 ID，唯一接续保留原 ID 和采购事实，歧义/丢失进度停止操作。多成品电缆不再漏行，小于1米的换算率按实际处理，旧米数不能向上取整为根数。入库预览和执行共用身份校验。上述采购连续性不等于已允许 ID＋旧型号写入；受保护改名、完整规格修订和保存引用的写入授权仍待接入。

配方库存查询使用公共服务中的保存引用只读解析，支持按 ID 查询、精确供应商、异常/null库存与现名/原名分列；线圈明确 ID 不回退到其他方案，非库存费用不显示缺货，损坏 BOM 不吞为空结果。Query 采用同一只读事务，未修改快照。页面快速切换配方时忽略旧请求结果。配方库存只读查询通过保存的 ID 读取现名和库存，旧型号不再用于匹配；供应商冲突、失效 ID 和停用仍须核对。新写入仍使用严格身份校验，此读取不授权继续采购入库。

活动订单列表、详情和采购总览已接入保存引用的采购现名视图：同一只读事务内按固定 ID 读取名称；保留原采购行 ID、实际价格、供应商和进度，电缆/浮球配置身份不随显示名变化。旧采购行缺少 ID 且无法唯一接续时仍拒绝。已关闭/已取消订单已通过独立历史名称装配读取现名，不重算计划或修改原采购事实；无 ID、缺失、停用、损坏和超限明确区分。生产准备和写操作尚未接入；严格命令构建与查询读取分别调用，不由客户端字段选择。

零件保存已增加过渡改名保护：PATCH要求版本，资料预览绑定引用源哈希，事务内重查；已知引用、历史旁路绑定、不完整盘点、同供应商撞名或预览后源变化均拒绝。价格等不改型号的保存继续可用。此保护不等于受保护改名命令完成，仍不能让已有引用的零件安全改名。
