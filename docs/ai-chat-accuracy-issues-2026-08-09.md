## 问题 1（工具缺陷，优先级高）：`search_parts` 不支持排序，"最值"类问题必错

### 现象

问"价格最高的零件是哪个"，AI 回答"油封 `10*22*5`，0.18 元"，实际是 `SPA 3 叶`/`SPA 3叶轮`，147 元——相差约 800 倍，且回答语气确定，无任何不确定性提示。

### 根因

- 工具定义 `api/routes/ai/tools.cjs` 中 `search_parts`（约 1286 行）只有关键词/类别/供应商/库存状态/价格区间参数，**没有 `sortBy` / `sortOrder` 参数**。
- 执行器 `api/routes/ai/executors/queryExecutors.cjs` 的 `case 'search_parts'`（约 424 行）直接把参数透传给 `GET /api/parts`，该接口按插入顺序返回，不支持排序。
- 模型拿到无序列表后自行"挑选"最大值，挑错了也无法察觉。

影响面：所有"最贵/最便宜/库存最多/最少/最新"之类的最值、Top-N 问题都会答错。

### 修复方向

1. `GET /api/parts`（`api/routes/parts.cjs`）增加 `sortBy`（`price` / `stock` / `updated_at` / `id`）和 `sortOrder`（`asc` / `desc`）查询参数，在 SQL 层排序（注意 `sortBy` 白名单校验，防注入）。
2. `search_parts` 工具定义和执行器同步增加这两个参数，并在 `description` 中明确说明："查询最贵/最便宜/库存最多等最值问题时，必须设置 sortBy + sortOrder 并配合 limit=1 或较小 limit"。
3. 回归验证：问"价格最高的零件"应回答 `SPA 3 叶`/`SPA 3叶轮` ¥147；问"库存最少的零件"（stock>0 口径）应回答 `14*28*38`（500）或按实际数据。

## 问题 2（模型计数幻觉，优先级中）：长列表的分类小计数字是编造的

### 现象

问"库存为 0 的零件有哪些"，工具正确返回全部 124 项，AI 总数答对（124），但自行添加的分类小计大量错误：

| 品类 | AI 标注 | 实际（SQL 直查） | AI 列出条目数 |
|---|---|---|---|
| 油封 | 66 项 ❌ | 51 | 51（列表完整，计数错） |
| 螺丝 | 12 项 ❌ | 15 | 15（列表完整，计数错） |
| 泵壳 | 8 项 ❌ | 9 | 9（列表完整，计数错） |
| 包装 | 10 项 ❌ | 13 | 11（漏 2 条） |
| 皮垫 | 5 项 ❌ | 6 | 5（漏 1 条） |

规律：模型转录长列表时会漏条目，且手写的"N 项"小计基本靠猜。

### 修复方向

1. **首选（确定性最高）**：在 `queryExecutors.cjs` 的 `search_parts` 返回结构中增加服务端聚合字段，例如：
   ```js
   categorySummary: [ { category: '油封', count: 51 }, ... ]  // 服务端 SQL group by 得出
   ```
   已有 `supplierCounts` 的类似逻辑可参考（约 432 行）。让模型直接引用算好的数字。
2. **辅助**：在系统提示词（`api/services/aiPromptComposer.cjs`）中增加规则：列举清单时不得手写"共 N 项"小计，必须引用工具返回的 `count` / 聚合字段；列表超过一定长度时按工具返回原样呈现，不要凭记忆重排或截断。
3. 回归验证：再问"库存为 0 的零件有哪些"，各品类小计应与 SQL `GROUP BY category` 结果一致。

## 附：本次测试的环境背景（非代码问题，无需修复）

- 从生产库同步数据后，`runtime_settings` 表中 `aiProvider=kimi` 的覆盖值被带到本地；加密的 `kimiApiKey` 依赖生产机 `JWT_SECRET` 解密（`api/services/runtimeConfig.cjs` 约 185 行），本地密钥不同导致解密失败，报"未配置 KIMI_API_KEY"。本地已改为 `deepseek` 临时绕过。这属于环境差异，但可以考虑：解密失败时在日志/设置页给出更明确的提示（"密钥无法在本机解密，请重新填写"），而不是笼统的"未配置"。

## 修复记录（2026-08-09）

### 改动内容

1. **`api/services/partQueries.cjs`**：`listParts` 新增 `sortBy`（白名单：`price`/`stock`/`model`/`updatedAt`）与 `sortOrder`（`asc`/`desc`，默认 `desc`），排序作用于过滤结果且先于 `limit` 截断；非法值返回 400（`INVALID_SORTBY`/`INVALID_SORTORDER`）。
2. **`api/routes/parts.cjs`**：`GET /api/parts` 透传 `sortBy`/`sortOrder`。
3. **`api/routes/ai/tools.cjs`**：`search_parts` 工具新增 `sortBy`/`sortOrder` 参数，description 明确要求最值/排名问题必须排序取 Top-N；`limit` 描述同步放开为"配合排序取最值排名时也可传入"。
4. **`api/routes/ai/executors/queryExecutors.cjs`**：透传排序参数；返回新增 `categorySummary`（服务端按品类统计）与 `aggregationNote`（声明 count/聚合字段为权威数字）。
5. **`api/services/aiPromptComposer.cjs`**：核心规则新增两条——计数必须引用权威字段不得自行清点；最值/排名问题必须用排序参数，工具不支持时如实说明。
6. **测试**：`tests/partQueries.test.cjs` 新增排序与注入拒绝用例；`tests/aiExecutorBehavior.test.cjs` 更新 filters 契约断言并新增排序透传用例。全套 988 个测试通过，lint 通过。

### 回归验证（实测 AI 回答）

- 问"价格最高的零件"→ 回答 `SPA 3 叶`（孚元）**147 元** ✅（模型主动使用 `sortBy=price, sortOrder=desc, limit=1`）
- 问"库存为 0 的零件按品类分组并给出数量"→ 各品类小计与 SQL `GROUP BY` 完全一致（油封 51、螺丝 15、包装 13、泵壳 9、电容 9、电缆线 7、皮垫 6、轴承 5、浮球 5、配件 4，合计 124）✅

### 已知残余瑕疵（低优先级）

- 最值问题配合 `limit=1` 时，模型可能把工具返回的 `count=1` 误表述为"零件库中共 1 个零件"之类的措辞（结论本身正确）。如介意，可在执行器返回中区分 `matchedCount`（过滤命中总数）与 `returnedCount`（本次返回条数）的语义说明。
