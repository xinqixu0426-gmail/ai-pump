# 前端状态边界

> 更新日期：2026-08-03。本文定义当前 Next 前端的远端数据、页面状态和服务端数据边界。后续新增页面、组件或 API 调用必须遵守本文。

## 1. 总原则

前端状态只负责组织交互，不承载新的业务口径。

- 服务端是权威数据源，业务写入以后端 API 和服务层结果为准。
- 全局状态只保存跨页面共享、可复用的远端列表缓存和全局 UI 状态。
- 页面本地状态只保存当前页面的草稿、筛选、弹窗、步骤和临时交互。
- 派生数据放到纯 helper、selector 或后端接口中，不把计算结果长期塞回全局 store。
- 增删改后必须重新拉取对应资源，不能只靠前端局部拼接数据假装成功。

## 2. 全局状态可以保存什么

当前全局状态可保存这些类别：

| 类别 | 示例 | 说明 |
|---|---|---|
| 共享远端列表 | `parts`、`recipes`、`orders`、`templates`、`customers`、`quotations` | 多页面会复用，允许 30 秒软缓存 |
| 共享加载状态 | `loading`、`error`、`loadedAt` | 与远端列表一一对应 |
| 全局反馈 | snackbar、全局错误提示 | 只用于跨页面提示，不保存业务草稿 |

新增全局字段或共享缓存前必须确认：

- 是否至少两个页面都需要同一份数据；
- 是否可以通过现有 API 重新拉取；
- 是否有明确的强制刷新路径；
- 是否有 mutation 后的硬刷新路径；
- 是否不会把表单草稿、弹窗状态或临时筛选扩散成全局状态。

## 3. 页面本地状态负责什么

以下内容必须留在页面或局部组件，不进入全局状态：

- 表单草稿、未保存输入、步骤条当前步骤；
- 弹窗开关、当前选中行、临时编辑对象；
- 搜索、筛选、排序、分页、表格列显示；
- 单次请求的 saving/submitting/importing 状态；
- AI 对话、转子出图、打印、下载等会话状态；
- 只服务当前页面的预览数据和临时校验结果。

复杂页面可以把规则抽到 `apps/web-next/lib/*` 或专用 helper，但 helper 必须保持纯函数优先，不直接读写全局状态。

## 4. 跨资源刷新规则

写操作完成后，按下表重新拉取相关资源。这是当前前端数据一致性红线，不能用局部 splice/push 替代。

| 写入资源 | 必须刷新 | 视页面需要刷新或重算 |
|---|---|---|
| 零件 CRUD | 重拉零件列表 | 配方/订单页面若展示当前成本或库存预检，需要重新计算页面派生数据 |
| 批量库存 | 重拉零件列表 | 订单详情、采购中心、生产确认弹窗需要重新拉取或重新计算库存状态 |
| 配方 CRUD | 重拉配方列表 | 订单表单、报价表单正在选择配方时刷新配方列表 |
| 模板/型号变体 | 重拉模板或型号变体列表 | 配方表单上下文、常用配置选择器重新取数 |
| 客户 CRUD | 重拉客户列表 | 报价页面客户选项和客户统计重算 |
| 报价 CRUD/状态变更 | 重拉报价列表 | 报价转订单成功后同时重拉订单列表 |
| 订单 CRUD/状态变更 | 重拉订单列表 | 涉及入库或扣库存时同时重拉零件列表 |
| 转子历史 | 当前页面重拉历史 | 不进入全局 store，除非未来多个页面复用 |

## 5. 缓存与乐观更新

- 共享远端列表默认可保留短缓存，当前约定为 30 秒。
- 路由进入时可以软加载，写入后必须硬刷新。
- 库存、订单、配方、报价和成本相关数据禁止全局乐观写入。
- 仅纯 UI 交互可以本地乐观展示，例如展开行、选中项、临时排序。

## 6. 派生数据位置

派生数据按优先级放置：

1. 影响业务结果、成本、库存、订单状态的，优先放后端服务/API。
2. 只影响前端展示且可重复计算的，放 `apps/web-next/lib/*`、`*Summary.ts`、`*Selectors.ts` 或页面同级纯 helper。
3. 只影响单个组件视觉的，放组件内部 `useMemo`。

禁止把以下内容作为长期状态保存：

- 总成本、利润、采购缺口等可由源数据重新计算的结果；
- 表格筛选后的列表；
- 从 JSON 字段解析出的临时对象；
- 已经可以由后端 API 返回的权威快照。

AI 会话列表与消息正文属于服务端持久化数据。前端只保存当前打开会话、输入草稿、流式响应和抽屉状态；切换会话必须重新读取服务端记录。

## 7. 大型工作台组件边界

`recipes-view.tsx`、`ai-view.tsx`、`knowledge-view.tsx` 和
`quotations-view.tsx` 已进入渐进瘦身范围。瘦身目标不是减少总代码行数，而是让每个
文件只有一个主要变化原因，降低状态、异步请求和弹层之间的耦合。

- 超过约 1,500 行或同时承担 3 个以上独立业务域时，必须评估拆分；
- 超过约 2,500 行时，不继续直接叠加大型功能，优先提取稳定业务区块；
- 按状态所有权、业务职责和异步生命周期拆分，禁止只为缩短文件机械切碎 JSX；
- 顶层页面负责资源加载和跨区协调，子组件不自行创建第二份业务草稿；
- 拆分不得改变后端事实来源、API 请求层、写后刷新和未保存保护。

## 8. 开发验收清单

每改一个页面，必须自查：

- 新 API 请求是否都走 `proxyRequest()`、`proxyFetch()` 或 `proxyStreamFetch()`；
- 写入后是否重新拉取对应资源；
- 页面草稿是否仍为页面本地状态；
- 业务规则是否在后端服务或 `apps/web-next/lib` helper 中；
- 是否没有新增裸 `fetch()`、裸成本公式、裸 `Id/CreatedAt/UpdatedAt` 依赖；
- 是否没有继续扩大已经进入瘦身范围的巨型组件；
- 是否保留加载、空态、错误、保存中和失败提示。
