# 业务流程说明

> 更新于 2026-08-29。本文是当前版本的业务流程基准。后续新增功能可以调整页面结构和交互方式，但不得改变这里定义的写库点、成本快照边界和状态流转语义。

## 1. 总流程

```text
维护基础数据
  -> 建立泵壳模板
  -> 创建配方：选择泵壳、线圈和选配
  -> 保存成本快照
  -> 客户报价
  -> 报价转订单或直接创建订单
  -> 生成采购清单和生产待办
  -> 采购中心登记下单进度
  -> 订单详情登记到货和分批入库
  -> 采购完成后人工关闭订单
```

## 2. 业务对象边界

| 对象 | 职责 | 不承担的职责 |
|---|---|---|
| 零件 | 维护型号、分类、供应商、价格、库存和备注元数据 | 不保存配方选择结果 |
| 线圈 | 维护标准直径、俗称、材质、槽眼和测试/正式/停用绕组方案；每套方案选择“计算计价”或“供应商套件价”，并记录默认线径/电容及主副绕组备忘 | 不维护材质默认单价；套件价不拆分定子、铜重和加工费，也不参与插值/外推、铜价同步或定子单片价批量修改；只有正式方案参与正式成本、正式选择并维护业务库存；配方保存时生成快照；绕组技术备忘不参与成本 |
| 泵壳模板 | 保存泵壳套件或自由搭配规则、固定配件、人工工资、表面处理工艺和转子默认参数；套件模式引用零件库整套泵壳，泵壳零件型号改名时同步关联模板，历史模板与当前零件仅相差唯一尺寸后缀时兼容识别；自由搭配的组合名称可手输或选择泵壳型号，计入成本的单件和供应商小套件父项数量必须为正数，父型号只能绑定零件库“泵壳搭配”分类；组件只保存正式字段，客户端临时字段和未知字段忽略；型号和供应商支持输入检索，已有记录自动带入目录价，新“型号 + 供应商”可在当前表单以正数单价直接建档为零库存零件；切换标签页回来时只刷新零件目录，不重置模板草稿；固定配件的型号候选按名称识别分类，例如花板/油缸轴承只检索“轴承”，机械/骨架油封只检索“油封”，螺丝类只检索“螺丝”，无法识别的自定义名称才回退到全部非包装零件；小套件父项按供应商报价整体计价和管理库存，内部组成可记录正数数量与参考单价，并显示组成参考合计和套件差额；机筒从铝机筒、不锈钢拉伸筒、铁机筒中选择，只有独立的不锈钢拉伸筒按长度动态计价 | 不代表最终产品 BOM；自由搭配模板名不承担库存；多个尺寸后缀候选并存时禁止猜测关联；小套件组成项及其参考单价不单独计价、扣库存或参与零价检查 |
| 常用配置（历史兼容） | 保存同一模板下的高频线圈、机筒、长螺丝和叶轮组合 | 不作为新建配方的必经步骤；修改后不反写历史配方 |
| 配方 | 保存产品 BOM、动态配置、客户可选配置范围、人工管理费、成本和技术参数快照；选配件或包装型号尚未建档时，可在当前配方草稿内完成正式零件建档，回读后自动绑定 `partId`、供应商和目录价，包装同时绑定正式二级分类；切回页面只刷新零件目录，不重置草稿 | 不随零件或模板后续改价、改规则自动变化；不修改历史报价或订单快照；不允许未建档占位零件绕过正式成本与身份校验 |
| 报价 | 基于配方做客户级价格和配置覆盖 | 不修改原配方 |
| 订单 | 以稳定客户 ID 保存客户名称快照、合同、订单明细、锁定成本、售价、采购清单和待办快照 | 不反向修改报价或配方；客户改名不切断订单归属 |
| 采购中心 | 按未完成订单聚合采购需求并标记采购进度 | 不增加库存 |
| 配方库存视图 | 按配方 BOM 展示配件当前库存和状态 | 不执行生产或修改库存 |

模板和配方中的就地零件建档统一复用正式 `parts.create`：整套泵壳、模板固定配件、配方选配件和包装材料都先回读目录并按“型号 + 供应商”判重，已有同类正式记录直接选中，跨类别冲突拒绝静默改类，新建成功后再次回读并回绑正式身份；这些调用显式使用 `duplicatePolicy=reject`，由正式创建命令在事务内重验身份，防止并发重复。零件资料页未使用该策略时，仍保留人工确认后重复建档的既有能力。整套泵壳和包装入口锁定各自分类，包装必须绑定正式二级分类；专用类别复用零件表单的型号规范化和当前就地表单展示的元数据字段，泵壳完整默认参数仍在零件资料页集中维护。线圈转子始终使用独立线圈方案，不进入零件库。

零件资料页把资料字段、绝对目标库存，以及电缆/浮球表单适用的全局设置作为一次整单保存：先由 `/api/parts/:id/save-preview` 绑定零件和设置版本，再由 `/api/parts/:id/save` 在同一事务提交；任一校验、审计或设置写入失败时整单回滚，网络重放不会把目标库存重复累加。独立入库、出库和 AI 库存调整仍只使用 `batch-stock-preview` → `batch-stock` 的增量库存命令。多选删除同样使用服务端批量预览与单个原子命令，禁止客户端并发单删造成半批成功。

模板只提供新配方的配置范围默认值；创建配方时复制后，两者不再联动。规则为空的历史模板和配方继续开放现有配置，显式规则才约束报价和订单可选范围。

## 3. 写库与只读边界

| 流程 | 主要入口 | 是否写库 | 写入内容 |
|---|---|---:|---|
| 零件查询/新增/修改/删除 | `/api/parts`、`/api/parts/:id/delete-preview`、`/api/parts/:id` | 查询否/写入是 | 查询由正式 `parts.list` 按关键词、类别、供应商、库存状态、数量和价格/库存数值边界筛选；无 `limit` 时返回全部，低库存统一为 1–5。正式 command 使用持久幂等；删除必须先取正式 Preview，再绑定 `expectedUpdatedAt` 与 `previewHash` 并通过 `safeUpdate` 软删除 |
| 零件批量调价 | `/api/parts/prices-preview` → `/api/parts/prices` | 预览否、执行是 | 只改 `parts.price`；AI/MCP 可按类别或用 `targets` 明确 1–8 个零件，后者先经正式 Query 以 `partId` 或完整 `model+supplier` 唯一绑定，再要求正式 Preview 无跳过、warning 或价格漂移并完整展示确认。预览绑定逐项版本和价格，整批价格、operation 与逐项强审计同一事务；执行后核对精确 changes 集合并回读正式价格 |
| 批量库存增减 | `/api/parts/batch-stock-preview` → `/api/parts/batch-stock` | 预览否、执行是 | 只改 `parts.stock`；服务端确认 token 绑定 `partId/delta/expectedUpdatedAt`，库存、operation 和强审计同一事务；AI 的单个/多个型号统一经 `adjust_part_stock` 生成一张确认卡，缺少 operation/audit 回执不得报成功；普通 PATCH 的 `stock` 只保留历史兼容 |
| 线圈新增/修改/删除 | `/api/coils`、`/api/coils/:id` | 是 | 定子组合、绕组方案状态、`pricingMode`、按模式保存的 `kitPrice/cost`、可选绕组技术备忘；计算方案保存传统成本组成，套件方案可保存不参与成本的可选 `wireWeight/copperBase` 价格参考，不保存单片价和加工费计算过程 |
| 模板新增/修改/删除 | `/api/templates`、`/api/templates/:id` | 是 | 泵壳模板、组件结构、工资默认值、转子默认参数；持久幂等，修改/删除绑定版本，模板与 operation/强审计同事务；任何历史配方引用都会阻止硬删除 |
| 模板成本/默认配方预览 | `/api/templates/:id/cost`、`/api/templates/:id/default-recipe` | 否 | 只返回计算结果或草稿 |
| 模板列表查询 | `GET /api/templates?shellModel?&description?&limit?` | 否 | 正式 `templates.list` 按型号、描述筛选；AI 不把模板查询误路由到零件或知识库 |
| BOM 草稿 | `/api/recipes/bom-draft` | 否 | 只生成标准化 BOM 草稿 |
| 配方成本草稿 | `/api/recipes/cost-draft` | 否 | 只生成保存前成本快照草稿 |
| 配方保存/修改/删除 | `/api/recipes/save-payload-draft` → `/api/recipes`、`/api/recipes/:id` | 预览否、执行是 | 配方 BOM、成本快照、技术参数和客户可选配置范围；可能自动新增缺失长螺丝零件。AI/MCP `update_recipe` 在确认前通过正式 Query 唯一绑定配方并生成整份保存草稿，明确清空规格使用 `clearSpec:true`（兼容 `newSpec:""`），确认 token 绑定版本与 Preview，确认后直接执行绑定 payload 并回读包含包装箱型/工资迁移状态的完整快照；旧喷漆工资未迁移时先停止。AI 删除同样绑定稳定 ID/版本后再确认，不会按名称重选目标 |
| 当前配方成本参考 | `/api/recipes/:id/cost`、`/api/recipes/current-costs` | 否 | 单配方入口只重算保存 `partsJson` 的当前配件参考价；批量当日入口按当前模板和配方参数重建完整 BOM 后重算 |
| 报价/订单配置试算 | `/api/recipes/:id/cost-preview` | 否 | 先按配方自己的配置范围校验，再按配方快照和受控覆盖项试算；包材按稳定零件 ID 和正式目录重新定价，不信任客户端快照价 |
| 客户新增/修改/删除 | `/api/customers`、`/api/customers/:id` | 是 | 持久幂等；修改/删除使用 `expectedUpdatedAt`；存在活动订单时禁止删除，历史订单和报价继续按稳定 ID 保留，客户与强审计同事务 |
| 客户列表/历史查询 | `GET /api/customers?id?&name?&limit?`、`GET /api/customers/:id/context` | 否 | 正式 `customers.list/history`；名称多义时返回候选，不任取第一项 |
| 报价列表查询 | `GET /api/quotations?status?&customerName?&limit?` | 否 | 正式 Query 按状态精确筛选、按客户名称模糊筛选；页面和 AI 不读取全量后自行判断状态 |
| 订单列表/采购汇总查询 | `GET /api/orders?status?&customerName?&contractNo?&limit?`、`GET /api/orders/purchase-overview` | 否 | 状态枚举和参数严格校验；无 `limit` 时返回全部正式结果。V2 由模型理解“订单/单子/单据”等口语并提交结构化计划；“采购中的单子”选择 `get_recent_orders(status=采购中)`，只有明确询问采购任务、供应商、采购物料、待采购数量或采购进度时才选择采购总览。参数直接经 tool 唯一 schema 校验；`answerShape=count_with_brief` 时先回答数量，再给客户/创建日期简报 |
| 报价新增/修改/状态/删除 | `/api/quotations`、`/api/quotations/:id`、`/api/quotations/:id/status` | 是 | 先用保存草稿取得正式成本快照和 `previewHash`；命令使用持久幂等，覆盖/删除使用 `expectedUpdatedAt`，报价与强审计同事务 |
| 订单采购计划 | `/api/orders/purchase-plan` | 否 | 只生成采购清单和待办草稿 |
| 活动订单准备总览 | `/api/orders/readiness-overview` | 否 | 一次平衡全部活动订单库存，汇总准备结论、问题和下一步 |
| 订单生产准备检查 | `/api/orders/:id/readiness` | 否 | 只读核对订单、BOM、零件、线圈、采购和成本价格 |
| 订单准备处理方案 | `/api/orders/:id/readiness-plan` | 否 | 将检查问题转换为有依赖顺序的确认、人工和等待步骤 |
| 订单方案动作执行 | `GET /api/orders/:id/readiness-plan` → `POST /api/orders/:id/readiness-actions/:actionId` | 是 | 用户确认后用版本、预览哈希和幂等键绑定实时方案；事务内再次重验，只执行当前可确认步骤并返回标准回执和新方案 |
| 订单新增/修改/删除 | `/api/orders`、`/api/orders/:id` | 是 | 订单头、明细、锁定成本、售价、采购清单、待办和状态 |
| 采购中心整项下单 | `/api/orders/purchase-items/batch-draft`、`/api/orders/purchase-items/batch` | 预览否/执行是 | 先确认物料、影响订单和数量，再原子更新全部活动订单采购项；不入库 |
| 采购进度与分批入库 | `/api/orders/:id/purchase-items/progress-draft`、`/api/orders/:id/purchase-items/progress` | 预览否/执行是 | 保存前由正式预览绑定订单版本、平衡计划、数量与库存影响；仅入库增量在统一命令事务内增加库存 |
| 一次性全部入库 | `/api/orders/:id/complete-purchase-draft`、`/api/orders/:id/complete-purchase` | 预览否/执行是 | 先用正式平衡计划预览并绑定版本与物料哈希，再把剩余计划登记为下单、到货和入库，并进入采购完成 |
| 配方库存状态 | `/api/recipes/:id/inventory-status` | 否 | 普通配件读取零件库，线圈转子读取独立线圈库存；只返回当前库存和状态 |
| 转子出图 | `/api/rotor/draw-preview` → `/api/rotor/draw` | 预览否/执行是 | 正式预览统一校验参数并返回全部安全警报；Web 展示警报后由用户明确确认，AI 遇警报停止执行；确认后才登记任务、历史和审计并启动 FreeCAD |
| 转子自然语言整理 | `/api/rotor/chat` | 否 | DeepSeek 只提取候选参数，确定性服务复用正式 Preview 的共享警报；返回警报或确认凭证，不直接启动 FreeCAD |
| 转子打印 | `/api/rotor/print/:jobId/preview` → `/api/rotor/print/:jobId` | 预览否/执行外部副作用 | 预览校验成功图纸和文件版本并展示默认打印机警报；确认后才发送打印任务 |
| 转子参数暂存 | `/api/rotor/save` | 是 | 保存 `status=saved` 的历史记录 |

## 4. 成本快照规则

成本分三类，业务实现和页面展示都不能混用：

| 成本类型 | 生成时机 | 允许变化 | 用途 |
|---|---|---|---|
| 当前重算参考 | 查看或手动试算时 | 会随零件、线圈、铜价、设置变化 | 风险提示、人工复核、AI 查询 |
| 配方保存快照 | 新建或修改配方保存前 | 保存后不自动变 | 配方详情、报价默认基线、订单来源 |
| 订单锁定成本 | 创建订单、报价转订单或追加订单明细时 | 保存后不自动变 | 订单利润、历史追溯、采购和生产依据 |

约束：

- 配方页面可通过 `POST /api/recipes/cost-draft` 展示成本草稿；正式 `save-payload-draft` 必须再根据表单、模板、线圈和所选零件重建权威 BOM 与保存快照，不能采用客户端草稿中的零件价格或合计。
- 模板的 `configurationPolicyJson` 是新建配方的默认规则；创建时复制到配方，之后模板与配方各自演进。历史模板或配方该字段为空时按 `legacy_open` 开放模式读取，避免升级后改变既有业务。
- 显式规则为版本化白名单：只限制已配置的字段，配方当前基线值始终有效。包装白名单使用稳定 `partId`，表面处理以“工艺 + 成本”成对限制；不在范围内的报价或订单覆盖返回 `422`。
- 配方保存 payload 和正式写入口必须检查完整 BOM；任一项目的快照单价缺失、无效或小于等于 0 时阻止保存，并提示先补齐零件型号和单价。
- 新保存的 BOM 每行带明确 `costRole` 和 `configurationDependencies`。浮球、电缆、包材、线圈、电容、机筒和长螺丝不再由报价/订单各自猜测；线圈规格或片数变化时必须按目标线圈方案同步重算电容。
- 进入正式成本的新普通零件优先使用 `partId`；缺少 ID 时只允许“型号 + 供应商”精确唯一匹配，无供应商时仅同型号唯一候选可兼容绑定。多个供应商候选时拒绝用最低价或任意一条代替身份。历史已锁定快照只保留兼容读取，不被迁移重写。
- 报价和直接订单的客户配置覆盖必须通过 `POST /api/recipes/:id/cost-preview` 试算，并在正式保存时由后端再次重算。
- 报价转订单必须保存展开后的 BOM 快照，不能只保存 overrides。
- 订单创建和追加明细的基础配方必须具备完整且大于 0 的 `savedTotalCost` 与保存 BOM；没有覆盖时直接锁定该快照，有客户配置覆盖时由共享配置快照服务基于配方重算并锁定最终成本和 BOM。任一结果不完整时阻止建单。
- 前端可以有展示级预览，但正式保存、报价和订单不得使用前端自算成本作为权威值。
- 当日完整成本存在未定价 BOM 项时必须标记为不完整并停止输出正式总金额；部分汇总只能用于诊断，不能进入报价、订单或利润计算。

## 5. 报价流程

1. 选择客户，带入客户默认利润率。
2. 选择基础配方，读取配方保存快照作为默认成本基线。
3. 报价页面当前可覆盖是否带浮球、电缆米数、外包装（牛皮纸箱/彩印箱/木箱）、泡沫型号和是否含珍珠棉；选项先按配方规则过滤，历史开放配方继续展示现有选项。线圈、机筒和表面处理在报价页只展示配方值。后端受控字段全集及未知字段拒绝规则见 `api-reference.md`。
4. 覆盖项通过 `POST /api/recipes/:id/cost-preview` 试算。线圈配置无法计价时停止报价；可插值或外推但没有正式库存方案时明确提示，后续订单生产准备仍会阻塞，不能把计算结果冒充可采购库存型号。
5. “不锈钢接轴”不进入模板或配方基线，报价和订单默认关闭。客户明确要求时启用，费用默认读取全局 6 元并只允许在 5–8 元内调整；服务端将“普通 45 号钢轴外露电机部分摩擦焊接不锈钢轴”锁为转子工艺要求，生成独立非库存成本行，不改写线圈转子整套基础成本。
5. 报价保存时后端重新试算，并把完整 `bomSnapshot`、`costSnapshot`、覆盖参数、单位成本和销售单价写入 `quotations.itemsJson`。报价阶段数量可不填；只要任一明细数量未确认，明细数量及整张报价的 `totalCost/totalPrice` 均保持 `null`，列表和统计显示“待数量确认”，不得默认按 1 台生成总金额。新建报价的询价附件、人工核对摘要和摘要来源也由保存草稿规范化并绑定同一个 `previewHash`。新增/修改网络重试复用同一幂等键，不会重复建报价或重复关联附件。
6. 已建报价仅通过 `GET /api/quotations/:id/inquiry-summary` 查看保存时的询价附件和摘要；详情页不提供二次上传、重新归纳或编辑，避免把建单后的资料误当成原始询价依据。
7. 查询某一状态报价时，调用 `GET /api/quotations` 并传入正式 `status` 条件；“列出还在报价中的报价”直接使用 `status=报价中`，不先读取全量再由页面或 AI 归类。
8. “报价中”超过一个月由 API 启动补跑及每天北京时间 00:05 的维护任务标记为“已过时”；读取列表不产生业务写入。
9. 新建报价时使用默认收起的“询价助手”工具栏上传客户发来的图片、Word、Excel、PDF、CSV 和文本询价附件；展开后桌面端以 480px 右侧辅助面板、窄屏以全屏面板展示“原始附件 / AI 归纳 / 待确认”，主报价表单不再被大段摘要纵向挤占。单文件或最多 4 个来源由专用只读接口强制交给现有 Kimi 开放平台配置：图片直接传原图，文档通过 Kimi 文件接口抽取，不依赖本地 OCR，也不静默回退 DeepSeek；失败时明确提示用户重试。Kimi 归纳产品、数量、技术、包装、交期和待确认要求后，再据此选择配方和填写价格。创建报价时原件与核对后的摘要一并保存，但摘要不自动修改正式报价产品、数量、成本或价格；已建报价详情不再提供补传入口。

禁止事项：

- 报价覆盖不得修改原配方。
- 报价保存不得只保存 UI 临时状态，必须能从 `itemsJson` 复原明细。
- 报价转订单不得复用未展开的 overrides 作为订单 BOM。

## 6. 订单流程

### 6.1 直接创建订单

1. 选择正式客户并提交稳定 `customerId`，填写合同号和备注；客户名称只保存当时快照。
2. 添加一个或多个基础配方明细；每条明细默认继承配方配置，客户有差异时只能在配方规则允许范围内修改浮球、电缆长度、包装、线圈片数、机筒长度和表面处理；线圈规格、材质和槽眼目前只展示配方值。
3. 每个明细提交 `recipeId/qty/profitMargin/unitPrice/configurationOverrides` 等业务输入；成品型号、配置摘要、最终单位成本、配置快照和 BOM 由后端读取正式配方并重新试算，客户端计算结果不作为事实。
4. 调用 `POST /api/orders/save-payload-draft` 生成保存 payload；后端锁定最终 `configurationSnapshot/costSnapshot/partsJson`，忽略客户端采购清单、待办和包材快照价，并按正式包材目录、最终 BOM、精确供应商身份及全部活动订单实时库存重新生成。不锈钢接轴作为 `rotorProcess` 工艺行进入订单 BOM 与成本快照，但不作为零件或线圈生成采购需求；生产按冻结的 `rotorShaftProcess` 执行。线圈只有计算成本但没有正式库存方案时保留 warning；订单仍可人工确认，但生产准备检查会保持 blocked，处理方案中的后续步骤要求先建立正式线圈方案。
5. 保存订单，初始状态为 `待确认`；人工确认后进入采购流程。

### 6.2 报价转订单

1. 从报价明细读取客户、报价单价和保存时已经展开的 BOM/成本快照；客户确认报价后，由工厂填写每个产品的最终订单数量。
2. 调用 `POST /api/quotations/:id/order-draft` 并提交最终 `itemQuantities`，预览订单及采购计划，同时取得报价 `expectedUpdatedAt`、绑定数量的确认内容 `previewHash` 和建议幂等键。缺少任一数量时不得生成订单预览；报价中冻结的不锈钢接轴状态、费用、工艺和 BOM 行原样继承，转换时不按当前全局默认重算。
3. 人工或 AI 确认后，使用同一数量、版本和预览哈希调用 `POST /api/quotations/:id/convert`；AI 还必须经过服务端 confirmation token，并复用确认操作的 `operationId` 作为幂等键。
4. 后端在同一事务内创建订单、保存报价与订单关联、把报价更新为 `已转订单`、保存 operation 回执并写入两条强审计。
5. 相同请求重试返回原回执；幂等键异参复用、报价版本冲突、活动订单/库存变化导致的预览冲突、重复或越级转单返回 409，且不会留下部分订单、状态或审计。
6. 兼容调用可暂不传 `Idempotency-Key/expectedUpdatedAt`，但不具备协议级重试和并发保护；新增调用不得使用兼容模式。

### 6.3 订单受控修改

1. “待确认”订单可修改核心内容；“待采购”只有在所有采购项的已下单、已到货、已入库数量均为 0 时可修改。一旦出现采购进度，必须拒绝核心修改，后续变更单、退料和差量采购不在当前流程内。
2. 修改客户、合同号、备注、产品、数量、客户配置或售价前必须填写原因。页面先调用 `POST /api/orders/save-payload-draft`，展示服务端生成的字段变化、采购计划变化和售价低于成本警告，再由用户确认执行 `PATCH /api/orders/:id`。
3. 只改数量、售价或订单头时继续使用订单已锁定的成本、BOM 和配置快照，不受配方后来改价或改规则影响；明确修改客户配置时才按当前配方规则和成本引擎重算该明细。人工修改售价后保持该售价固定，只重算利润率。
4. 服务端以“用编辑草稿替换当前订单”的方式参与全部活动订单库存平衡，再重建采购清单和待办，不能把修改前后的同一订单重复占用库存。
5. 执行时再次校验订单版本、状态、采购进度和预览哈希。订单、修订记录、operation 和强审计在同一事务提交；每次修订保存原因、操作者、时间、修改前后完整业务快照和结构化差异，订单详情可只读回看且不能覆盖历史。

### 6.4 订单状态

| 状态 | 含义 | 典型触发 |
|---|---|---|
| 待确认 | 直接创建后尚未确认核心明细 | 新建订单 |
| 待采购 | 已确认，尚未登记下单 | 确认订单 |
| 采购中 | 已有下单、到货或部分入库 | 数量进度自动推导 |
| 采购完成 | 全部计划数量已入库，但订单尚未关闭 | 数量进度自动推导 |
| 已关闭 | 业务事项已结束，且库存去向已明确 | 采购完成后确认“已人工领用出库”或“释放预留” |
| 已取消 | 订单不再继续执行 | 待确认/待采购/采购中填写原因后取消 |

订单状态不能任意倒退。采购中和采购完成不能手工指定；已关闭、已取消为终态。关闭不会隐式扣库：选择“已人工领用出库”表示仓库已在线下完成领用，系统只留痕；选择“释放预留”必须写原因。报价转订单生成的订单已经经过客户确认，因此直接进入待采购。

## 7. 采购与库存流程

### 7.1 采购清单生成

- 输入为订单明细的 `partsJson × qty`。
- “外包装估算”等成本占位项不进入正式采购清单；订单确认前必须改为零件库中具体的外包装型号和供应商，否则生产准备检查返回数据阻塞。
- 真实零件以 `partId` 为稳定身份；无 ID 的兼容数据按“型号 + 供应商”精确绑定。未写供应商时只有同型号唯一候选才允许绑定，禁止借用任意同型号供应商库存。
- 普通直接建单和报价转订单进入新订单前共用同一个 BOM 身份入口；历史配方或报价快照只补齐 `partId`、不改锁定价格，无法唯一绑定时阻止建单，已有历史订单保持不变。
- 线圈转子不进入零件库；精确匹配规格、片数、材质和槽眼的正式方案按 `coilId` 识别并以“套”为库存单位。
- 插值或外推得到但没有正式方案的线圈为非库存计算项，不伪造 `partId/coilId`。
- 全部活动订单按创建顺序共享库存，前序订单占用后，后序订单只使用剩余库存，避免同一库存重复分配。
- 采购中心汇总平衡后的 `needToBuy`。
- 参数化长螺丝可以借用基础螺丝供应商，但不能扣基础螺丝库存，也不能把基础螺丝 `partId` 写给目标长度采购项。配方保存时以 `dynamicRule=longScrewByBarrelLength` 识别机筒螺丝并自动建立缺失的目标长度零件；历史数据补建后，活动订单按“型号 + 供应商”自动改用真实 `partId`，并保留原有下单、到货和入库进度。

### 7.2 采购中心

- 采购中心只聚合未完成订单的采购需求。
- 采购中心汇总 `plannedQty/orderedQty/receivedQty/stockedQty`，可按供应商和型号执行整项下单，不增加库存。
- `GET /api/orders/purchase-overview` 只读汇总同一批活动订单的当前采购数量、供应商和待办明细；AI 查询“当前采购情况”时直接调用该接口，不从知识库或历史会话推断。
- 部分下单、实际采购价、实际供应商、到货和入库数量在订单详情逐项登记。
- 实际采购价未记录时，订单采购页可带入正式参考价并标明来源；普通零件使用单位一致的零件库当前单价，精确匹配正式线圈方案的线圈转子使用每套“总成本”：计算计价方案采用当前后端计算结果，供应商套件方案直接采用已保存的套件价。保存后锁定为实际采购价，不随参考价变化自动覆盖。线圈按片 `unitPrice` 不得直接带入按“套”采购的线圈转子；没有精确正式方案的插值或外推线圈不生成采购参考价。
- 经营看板按“订单锁定成本 + 已记录采购价差”计算调整后预计成本和利润。采购价差只比较已记录实际采购价、存在正式参考价且已经下单的数量；尚未登记的采购价格不冒充实际成本。

### 7.3 入库

- 采购中心“全部下单”先调用 `/api/orders/purchase-items/batch-draft`，按全部活动订单实时平衡计划返回受影响订单、数量、版本和预览哈希；人工确认后以同一幂等键执行 `/api/orders/purchase-items/batch`。
- 跨订单批量下单不增加库存；所有计划快照、订单状态、operation 和强审计在同一事务提交，任一订单版本或受影响集合变化都会拒绝旧预览。
- 入库发生在订单详情确认。
- 数量必须满足 `stockedQty ≤ receivedQty ≤ orderedQty`；`orderedQty` 超过 `plannedQty` 时必须明确确认超采。
- 每次提高 `stockedQty` 都只把增量加入库存，并在同一事务内记录 `stockInHistory` 批次。
- 普通零件入库前必须存在对应 `partId`，线圈转子入库前必须存在对应 `coilId`；任一校验失败时采购进度和库存一起回滚。
- 线圈采购入库增加 `coils.stock` 并写入 `coil_stock_movements`，订单号保存在流水引用中。
- 全部计划数量入库后自动进入采购完成；订单关闭是后续独立人工动作。
- 单项保存先调用 `POST /api/orders/:id/purchase-items/progress-draft`，绑定当前订单版本、全部活动订单平衡计划、采购数量和实际库存；Web 的“保存采购进度”是明确动作，涉及库存增加时还必须显示入库数量、采购/库存单位换算和入库后库存供人工确认。
- 执行 `POST /api/orders/:id/purchase-items/progress` 时提交同一 `expectedUpdatedAt/previewHash/Idempotency-Key`。平衡或库存漂移返回 409；入库增量、关联计划快照、订单、operation 和强审计任一失败都会整体回滚。
- 一键入库必须先调用 `POST /api/orders/:id/complete-purchase-draft`，由后端按全部活动订单和当前库存生成普通零件、正式线圈、非库存项及准确数量，并返回 `expectedUpdatedAt/previewHash/suggestedIdempotencyKey`。
- 人工确认后调用 `POST /api/orders/:id/complete-purchase`。新增调用必须提交相同版本、预览哈希和幂等键；确认后库存或平衡计划变化会返回 409 并要求重新预览。
- 只有普通零件与正式线圈会增加库存，非库存项只完成采购进度；平衡计划、零件库存、线圈库存与流水、订单状态、operation 回执和强审计在同一事务内提交。
- 相同请求重试返回原回执；旧调用暂可不传新字段，但不具备协议级重试、并发和确认内容绑定保护。一键入库不直接关闭订单。
- 采购入库只记录新到物料。系统不恢复生产执行模块，也不在订单关闭时自动扣料；实际领用由仓库分别通过零件库存调整和线圈库存调整登记出库。
- AI 按客户名或合同号追问订单采购明细时，先通过正式客户/订单目录解析目标，再读取订单详情；用户没有明确提供订单编号时不得生成或猜测 `orderId`。只读唯一高置信候选可透明绑定并说明正式名称，多候选必须停止并要求明确；原词零匹配时可在受限调查预算内缩短名称或改用合同号正式查询，预算结束仍无候选才回答未找到。

### 7.4 配方库存查看

- 配方详情通过 `GET /api/recipes/:id/inventory-status` 读取配件与线圈库存；线圈转子不依赖零件库。
- 按稳定 `partId` 或 `model + supplier` 精确匹配；缺少供应商时仅在同型号唯一候选下兼容绑定，不任取同型号库存。

### 7.5 订单生产准备检查

- `GET /api/orders/:id/readiness` 复用全部活动订单按顺序共享库存的计划结果，不建立第二套库存计算口径。
- 检查顺序固定为订单状态、配方与BOM、零件库存、线圈库存、采购进度、成本与价格。
- 当前可用库存覆盖需求时才可判定可生产；已下单、已到货但未入库仍属于待补料。
- 没有正式库存方案的计算型线圈、未绑定具体型号的外包装估算、没有零件库存映射的采购项、缺BOM或未确认订单返回数据阻塞。
- 库存满足但成本缺失、售价低于成本或来源配方不可追溯时返回待复核，不把商业风险伪装成物理缺料。
- 检查只给出结论、证据和建议入口，不确认订单、不自动采购、不调整库存。
- 页面只展示物料、库存和状态，不提供生产数量、生产确认或自动扣库存操作。
- 缺货、零件未建档和正式线圈方案缺失必须明确标记。

### 7.6 订单准备处理方案

- `GET /api/orders/:id/readiness-plan` 先执行同一套生产准备检查，再按数据修复、订单确认、采购下单、到货和入库依赖生成步骤。
- `confirmable` 步骤只携带未来确认所需的标准工具名称和参数，不在方案接口中执行；`manual`、`needs_input`、`monitor` 分别表示人工处理、等待业务决定和外部状态跟进。
- 缺BOM、普通物料未关联零件、计算型线圈没有正式库存方案时，处理方案中的确认订单步骤和后续采购步骤必须等待这些前置项完成；直接状态接口仍允许负责人独立确认订单，但不会绕过生产准备 blocked 结论。
- `/api/orders/lookup` 专供只读解析订单ID、客户名称和合同号，不调用会刷新采购缺口的订单列表接口。
- 本阶段仍不引入生产数量、生产确认、自动扣库存或独立生产执行模块。

### 7.7 订单方案动作执行

- AI 收到“执行第几步”后先刷新处理方案，不根据旧会话中的步骤状态直接写入。
- `execute_order_readiness_action` 是受确认保护的写工具；只有确认卡片批准后才调用订单标准动作接口。
- 服务端再次生成实时检查和方案，只允许白名单中仍为 `confirmable + available` 的动作；步骤已完成、已变化或受阻时返回 `409`。
- 当前自动动作限于确认订单并按实时进度进入采购流程、生成采购清单。人工修正BOM、补价格、采购下单、到货和入库仍走现有业务页面和标准接口。
- 执行结果返回更新后的订单和 `nextPlan`，AI 展示新的剩余步骤，形成“检查、计划、确认、执行、复查”闭环。

### 7.8 活动订单准备总览

- `GET /api/orders/readiness-overview` 只读取未关闭且未取消的订单，一次生成全部订单共享库存的平衡计划，再复用单订单检查和处理方案服务。
- 总览按数据阻塞、待补料、待复核、可生产排序；汇总数量与订单明细来自同一次计算，避免看板和 AI 使用不同口径。
- 每条订单明细只保留主要阻塞、风险、缺料和第一个未阻塞步骤，供管理看板快速判断；需要完整六步依据时仍读取单订单检查。
- `get_order_readiness_overview` 和管理看板“订单准备”页签均调用该只读接口，不确认订单、不更新采购、不调整库存，也不引入生产执行模块。

### 7.9 重点订单处理工作台

- 管理看板总览使用 `/orders?orderId=:id&view=readiness` 进入指定订单，不再只跳转到订单列表。
- 订单页面读取 `orderId` 后从标准订单列表定位订单，并按 `view` 恢复客户要求、生产准备、型号、采购或待办页签；关闭详情时清除 URL 中的订单上下文。
- “生产准备”页签并行读取 `/api/orders/:id/readiness` 和 `/api/orders/:id/readiness-plan`，展示完整检查依据、问题、缺料和依赖步骤；刷新只重新读取实时结论。
- 该页签不直接执行方案工具。订单确认、采购进度、入库、关闭和取消仍通过订单详情现有明确按钮和标准写接口完成。

### 7.10 订单页面上下文 AI

- 打开订单详情或切换客户要求、生产准备、执行档案、型号、采购、待办页签时，前端同步更新 URL，并把订单 ID 与当前页签作为独立 `pageContext` 传给右侧 AI。
- 页面上下文不进入用户消息或会话历史，只用于解析“这个订单”“它”“下一步怎么处理”等省略指代；明确订单编号和全部订单问题不会被当前页面覆盖。
- 后端只接受订单类型、正整数 ID 和白名单页签，不接收客户端标签、提示词、状态、金额或库存等业务事实。
- 解析后的问题仍先执行实时订单详情、生产准备检查或处理方案工具，页面上下文不能替代标准 API，也不会扩大 AI 写权限。

### 7.11 客户要求与确认知识

- 订单“客户要求”页签通过统一文件接口上传生产要求、包装要求、客户图片、Excel 或 PDF，并以 `order + customer_requirement` 关系保存；原文件只保存一份。
- “AI 归纳”在订单页面直接调用统一 AI 流式接口，并把结果原地填入客户要求编辑框，不跳转工作台、不要求复制粘贴。AI 只按附件原文生成分类草稿，把缺失和冲突内容列为待确认，不得把经验推断写成客户要求。
- AI 先展示归纳结果；只有用户明确要求保存时，`save_order_requirement_draft` 才生成确认卡片并调用草稿接口。AI 无权确认知识或撤销确认。
- 订单页面可以编辑归纳、选择本次依据文件并保存草稿。点击“确认进入知识库”后，最后确认版本合并到现有订单知识条目，自动刷新检索；原始附件本身不会仅因上传而被当作已确认事实。
- 已确认后继续编辑只产生待确认草稿，知识库继续使用上次确认版本，避免半成品覆盖正式知识。重新确认后替换；撤销确认后知识库移除客户要求，但草稿和原文件保留。
- 客户要求归档不修改订单产品、配方、采购或库存，也不恢复生产执行模块。后续生产资源和过程追溯基于确认知识继续扩展。

### 7.12 订单执行事实档案

- 订单“执行档案”页签使用多条时间线记录生产前资源与物料准备、生产中产能或供应商调整和过程异常、生产后质量与交付结果，不把全部过程压成一段不可追溯说明。
- 每条记录保存阶段、事实类型、标题、发生时间、事实说明和依据附件。附件复用统一订单文件对象，以 `execution_evidence` 区别客户原始要求，不复制原文件。
- 执行依据附件的“AI 归纳”同样原地填入当前事实说明，用户继续核对阶段、类型和正文；该动作只生成页面草稿，不自动调用保存或知识确认接口。
- 草稿可以反复修改或删除；人工点击“确认进入知识库”后，确认快照才合并到现有订单知识条目。修改草稿时旧确认事实继续可检索，重新确认才替换。
- 已确认记录引用的附件不能直接解除订单关联；先撤销确认，或重新确认一版不再引用该文件的内容。撤销后草稿和附件仍保留。
- `save_order_execution_draft` 只在用户明确要求保存已发生事实时生成确认卡片并新建草稿。AI 无权确认、撤销或删除正式事实。
- 执行档案只负责记录与追溯，不修改订单状态、配方、采购或库存，也不恢复已经取消的生产执行模块。生产准备页继续承载实时检查、方案和待办，两者不得混写。

### 7.13 只读订单知识包

- `GET /api/orders/:id/knowledge-package` 统一返回实时订单、采购、待办、生产准备和处理方案，以及最后一次人工确认的客户要求、执行事实和来源文件。
- 实时业务数据每次请求重新读取和计算，不依赖知识库同步；确认事实只读取 `confirmed_*` 快照，未确认草稿只计入待确认数量，不作为正文依据。
- AI 的单订单详情、生产准备和处理方案查询由能力注册表自动伴随调用 `get_order_knowledge_package`，不依赖模型根据问法自行决定是否检索。客户简称和合同号允许由正式 API 模糊匹配；具名订单列表查询唯一命中一张订单时也按正式结果 ID 自动补充知识包，多条命中时必须要求用户明确，不能猜选。
- 知识包只读，不确认事实、不执行生产、不修改订单、配方、采购或库存。伴随查询没有确认记录时不主动展开知识包；用户明确询问客户要求、执行档案或历史资料而系统没有记录时，才回答“未记录”。

### 7.14 统一管理待办中心

- `GET /api/workbench/action-center` 实时汇总订单准备、经营风险、数据质量、规则学习和知识库健康五类现有检查，不建立第二套业务判断规则。
- 待办按严重、较高、中等、较低优先级排序；同一订单的采购缺口由订单准备检查统一呈现，避免重复提醒。
- 每条待办提供来源、建议动作和对应业务页面入口。看板与 AI 使用同一结果，AI 可回答“今天最先需要处理什么”；当前单人管理场景不要求分配负责人或维护团队任务状态。
- 待办中心只读，不确认订单、不修改配方、不审核规则、不执行知识同步；处理动作继续在对应页面通过既有权限和确认流程完成。
- V7.1 后台每 5 分钟核对一次稳定待办键，记录首次出现、当前连续出现起点、消失时间和累计出现次数；普通打开看板不会触发写库。
- `management_action_events` 只追加出现、消失和再次出现事件。事项消失仅表示实时检查当前不再检出，不能推断是谁处理或为什么解决。
- 看板在当前待办旁显示持续时间和第几次出现，并展示最近消失记录；AI 只读使用同一生命周期信息。
- V7.2 从完整待办中自动选出最多 3 项“今日执行队列”。业务优先级始终优先，同级再比较持续时间、重复出现次数和影响数量，并显示每项排序依据。
- 今日执行队列只减少判断步骤，不隐藏其他待办、不建立负责人或手工状态；处理仍直达原业务页面，实时检查不再检出后由 V7.1 自动记录消失。
- V7.3 为每项队列返回统一处理路径：打开业务页面、需要业务判断、等待外部变化或 AI 可确认。看板显示下一步和完成标准，避免用户重新分析从哪里开始。
- 只有当前订单方案明确允许的“确认订单”和“生成采购清单”可交给 AI；点击后 AI 工作台预填处理请求，仍先刷新今日队列和订单方案，再展示确认卡片。其他事项不会因为进入执行队列而获得写权限。
- V7.4 在零件、配方、模板、订单、线圈、客户、报价、质量规则和知识库等核心业务写入成功后触发短延迟复查；连续操作自动合并，失败响应、只读查看、草稿和试算不触发。
- 复查后不再出现的事项自动转为已解决并进入归档记录，不要求人工勾选完成。归档只说明当前实时规则不再检出，保留首次出现、持续时间和再次出现事件。
- 看板和 AI 共用最近 24 小时处理进展，分别汇总自动归档、仍待处理、暂时受阻和反复出现；AI 不从会话历史猜测完成情况。

### 7.15 跨业务变更记忆

- 所有已登记且会改变正式业务事实、配置或资料的 Command 在成功完成后，以同一 `operationId` 追加一条统一业务事件；一次采购入库即使同时影响订单、零件或线圈，也只生成一条事件并列出全部关联对象。
- 领域 service 显式提供事件类型、主业务域、原因、关联实体和订单修订引用；公共命令执行器只校验并原子落库，不从底层表名或字段猜测业务语义。空操作、失败事务和幂等重放不会增加历史。
- `GET /api/business-changes` 和管理页面“业务变更”持有时间、数量、领域和实体筛选语义。AI 统一使用 `search_business_changes` 回答“今天有没有订单修改”或跨业务修改问题，不能改用管理待办、当前列表或聊天记录推断。
- 事件同步为 `change_event` 知识条目并进入现有 FTS/向量索引，支持“不锈钢接轴相关修改”等语义查找；结构化事件仍是精确事实，向量失败不改变总数。删除 AI 对话不会删除业务事件或已经确认的长期纠正规则。
- 覆盖范围按“是否改变正式业务事实、配置或资料”统一判断，不按页面逐个增加查询 API。订单、报价、采购、零件、配方、模板、线圈、客户、常用配置预设（历史技术类型 `model_variant`）、质量规则、转子档案、业务设置、文件、知识文档和工作流记录进入同一个中心；AI 对话/评测/反馈、索引重建、行情维护、解析进度和打印/生成过程仍留在各自技术记录中。

## 8. 知识库与 AI 会话

### 8.1 统一文件与知识边界

- PDF、Excel、CSV、文本和图片先保存为统一文件对象；相同内容按 SHA-256 复用，不为每个业务关系重复保存二进制。
- 客户、订单、配方和质量反馈等通用业务附件采用“只读预览 → 上传并归档”复合命令；文件对象与业务关联同一事务提交，目标变化或关联失败时不留下未引用文件。文件解析在事务提交后使用独立 operation，不把 OCR/文档解析放进 SQLite 长事务。
- “本轮 AI 分析”“关联客户/报价/配方/质量证据”“归档到知识库”是三个独立动作。业务附件关联不等于知识入库，只有明确归档的资料才进入跨会话检索。
- AI 工作台单个文件不超过 10MB，每条消息最多 4 个。PDF/表格解析和图片 OCR 只提供带来源位置与置信度的候选，不自动新增客户、配方、报价或技术参数。
- 配方页面上传的 `.xls/.xlsx` 性能测试报告属于正式配方技术档案；解析器保存逐条有效测试点，并由服务端确定性计算最高扬程、最大流量、最大电流、最高机组效率及各自对应测试点。AI 查询该水泵的流量、扬程、电流或效率时必须调用正式技术档案 Query，直接使用 `testCurve` 的测试点和服务端统计，不得自行挑选极值；知识快照及模板中的规定点、实测点、偏差均不得替代正式曲线结果。
- 文件价格不是正式成本。报价文件只能生成只读映射草稿，正式报价仍由配方成本 API 重新计算并由用户确认。
- 解除一个业务关联不删除原文件或其他关联；被已确认客户要求或执行事实引用的来源文件必须先撤销确认或确认不再引用的新版本。
- 原文件和解析结果用于追溯；AI 摘要不能替代原文，低置信度或冲突内容必须人工复核。

- `knowledge_entries` 是由正式业务数据生成的派生索引，不是新的业务事实来源。
- 同步按 `sourceTable + sourceId` 增量更新，原始数据失效时移除对应条目，并保留未变化条目的稳定 ID。
- 核心业务通过标准写入 helper 变更后自动提交知识刷新；连续写入短延迟合并，失败自动重试，人工同步只作为全量核对和恢复兜底。
- 自动、即时和人工同步的成功、失败及每次重试都会写入 `knowledge_sync_runs`；看板读取最近历史用于定位异常，记录最多保留 200 次。
- 健康检查只在自动同步关闭、等待或运行超时、未安排变化和失败未恢复时告警；没有业务变化不会因时间间隔产生假告警。人工恢复仍先确认再同步。
- FTS 与知识条目在同一事务内刷新；同步失败时保留上一版完整索引。
- AI 搜索结果必须能返回原始来源类型和来源 ID，业务判断仍以原资源 API 为准。
- 零件、订单、采购和配方的事实查询先由模型提交结构化意图、上下文依赖和最小 capability 步骤，再按能力注册表生成本轮 allowlist。tool 参数直接通过唯一 JSON schema，服务端不再用疑问词/状态词删减规则重写语义。正式接口返回零结果、未找到或业务失败后不得扩大为宽泛知识搜索；只有用途、经验、制度、外部资料等知识型问题进入知识检索。
- 系统外技术说明、文本、Excel、测试报告和 PDF 原件保存在 `knowledge_documents`，通过 `document` 知识条目进入现有检索；文本和 Excel 可检索提取正文，PDF 当前只使用人工填写的标题、说明和标签，不得推断未解析的图纸内容。
- 配方智能检查的学习反馈绑定当时的泵壳模板和配方版本；内容修改或模板变化后，旧反馈停止影响规则并进入待重新检查队列。
- 归档带有学习反馈的配方时，同一事务会立即刷新候选规则和已批准规则知识；归档证据只保留历史追溯，不再支持当前规则。
- 学习证据健康检查覆盖尚未形成候选规则的单条反馈，只提供复核队列，不自动恢复反馈、修改配方或批准规则。
- 数据质量看板的待复核反馈可按配方逐条打开，配方页会自动执行一次智能检查；用户根据当前配置重新确认对应提醒后，该反馈才重新成为有效学习证据。
- 原提醒重新出现时，页面会精确高亮并要求按当前配置重新判断；原提醒已经消失时，可确认已解决并将旧判断恢复为中性复核状态。服务端会再次执行当前配方智能检查，防止绕过页面误清理仍存在的提醒；该动作保留原始证据，不删除历史，也不会修改配方。
- 待复核任务按配方聚合；同一配方的多条反馈一次打开后按进度逐条处理，完成当前反馈后自动定位下一条，但每条仍需独立保存人工判断。
- 每次复核保存后展示规则学习刷新结果；暂时跳过只改变当前页面的处理顺序，不改变反馈状态。整组完成后清理复核参数，返回数据质量看板时重新读取健康队列。
- AI 会话完整保存在 SQLite；发送给模型的上下文只保留最近 10 条用户或助手消息。
- 历史会话中的写操作结果只用于回看，不能再次直接确认执行。

### 8.2 客户要求与订单执行档案

- 订单详情“客户要求”保存客户原始文件、AI 辅助归纳草稿和人工确认版本；AI 归纳只填充编辑框，不自动保存或确认。
- 未明确内容标记为“未提供”，冲突项单独列出。只有人工确认版本可以进入订单知识包，未确认草稿不能作为事实。
- “执行档案”按生产前、生产中、生产后记录已经发生的资源准备、供应商调整、过程异常、质量、交付和客户反馈；建议、预测、待办和未决定事项不能保存为执行事实。
- 已确认内容再次编辑时，知识库继续使用上一次确认版本；重新确认后才替换，撤销确认会移除正式知识但保留草稿和原始文件。
- 订单知识包只读聚合实时订单、采购、待办和生产准备状态，以及人工确认的客户要求和执行事实。两类来源必须明确区分；没有记录时直接说明“未记录”，不得用相似订单补写。

## 9. 允许调整的内容

可以调整：

- 页面布局、弹窗、步骤条、表格和筛选交互。
- 页面状态和资源缓存组织方式。
- API client 内部封装。
- 业务 helper 的文件结构。
- UI 组件库和动效实现。

必须保持不变：

- API 标准契约和路径。
- 写库点。
- 成本快照生成时机。
- 报价转订单保存展开 BOM 快照。
- 采购中心不入库。
- 入库通过订单业务动作 API；配方库存视图保持只读，零件与线圈分别使用自己的库存调整入口。

## 10. 开发检查清单

新增或调整业务功能时必须同步遵守：

- [前端状态边界](./frontend-state-boundary.md)：约束远端数据、页面本地状态、跨资源刷新和派生数据位置。
- [UI/交互约束](./ui-refactor-guidelines.md)：约束页面结构、动效、表单、表格和组件风格。

- 新页面是否只通过标准 API 入口写库。
- 保存动作是否明确调用后端权威成本接口。
- 只读预览是否没有写库副作用。
- 写操作后是否重新拉取对应资源。
- 新增 API 是否遵守 `docs/api-contract.md`、执行 `docs/api-sop.md`，并同步 `docs/api-reference.md`。
- 新增业务规则是否有 helper 或服务层测试，而不是只藏在页面组件里。
