# 业务流程说明

> 更新于 2026-07-23。本文是当前版本的业务流程基准。后续新增功能可以调整页面结构和交互方式，但不得改变这里定义的写库点、成本快照边界和状态流转语义。

## 1. 总流程

```text
维护基础数据
  -> 建立泵壳模板
  -> 创建配方：选择泵壳、线圈和选配
  -> 保存成本快照
  -> 客户报价
  -> 报价转订单或直接创建订单
  -> 生成采购清单和生产待办
  -> 采购中心登记下单进度
  -> 订单详情登记到货和分批入库
  -> 采购完成后人工关闭订单
```

## 2. 业务对象边界

| 对象 | 职责 | 不承担的职责 |
|---|---|---|
| 零件 | 维护型号、分类、供应商、价格、库存和备注元数据 | 不保存配方选择结果 |
| 线圈 | 维护标准直径、俗称、材质、槽眼和测试/正式绕组方案；正式方案记录片数、铜重、铁芯单片价、加工费、默认线径/电容及主副绕组备忘 | 不维护材质默认单价；测试/停用方案不参与正式成本；配方保存时生成快照；绕组技术备忘不参与成本 |
| 泵壳模板 | 保存泵壳套件或自由搭配规则、人工工资、表面处理工艺和转子默认参数；套件模式引用零件库整套泵壳，自由搭配的组合名称可手输或选择泵壳型号，组件型号只能绑定零件库“泵壳搭配”分类；机筒从铝机筒、不锈钢拉伸筒、铁机筒中选择，只有不锈钢拉伸筒按长度动态计价 | 不代表最终产品 BOM；自由搭配模板名不承担库存 |
| 常用配置（历史兼容） | 保存同一模板下的高频线圈、机筒、长螺丝和叶轮组合 | 不作为新建配方的必经步骤；修改后不反写历史配方 |
| 配方 | 保存产品 BOM、动态配置、人工管理费、成本和技术参数快照 | 不随零件或模板后续改价自动变化 |
| 报价 | 基于配方做客户级价格和配置覆盖 | 不修改原配方 |
| 订单 | 保存客户、合同、订单明细、锁定成本、售价、采购清单和待办快照 | 不反向修改报价或配方 |
| 采购中心 | 按未完成订单聚合采购需求并标记采购进度 | 不增加库存 |
| 配方库存视图 | 按配方 BOM 展示配件当前库存和状态 | 不执行生产或修改库存 |

## 3. 写库与只读边界

| 流程 | 主要入口 | 是否写库 | 写入内容 |
|---|---|---:|---|
| 零件新增/修改/删除 | `/api/parts`、`/api/parts/:id` | 是 | 零件基础数据；更新和删除必须走 `safeUpdate` / `softDelete` |
| 批量库存增减 | `/api/parts/batch-stock` | 是 | 只改 `parts.stock`；入参只接受 `{ partId, delta }` |
| 线圈新增/修改/删除 | `/api/coils`、`/api/coils/:id` | 是 | 定子组合、绕组方案状态、可选绕组技术备忘和计算后的 `cost` |
| 模板新增/修改/删除 | `/api/templates`、`/api/templates/:id` | 是 | 泵壳模板、组件结构、工资默认值、转子默认参数 |
| 模板成本/默认配方预览 | `/api/templates/:id/cost`、`/api/templates/:id/default-recipe` | 否 | 只返回计算结果或草稿 |
| BOM 草稿 | `/api/recipes/bom-draft` | 否 | 只生成标准化 BOM 草稿 |
| 配方成本草稿 | `/api/recipes/cost-draft` | 否 | 只生成保存前成本快照草稿 |
| 配方保存/修改/删除 | `/api/recipes`、`/api/recipes/:id` | 是 | 配方 BOM、成本快照、技术参数；可能自动新增缺失长螺丝零件 |
| 当前配方成本参考 | `/api/recipes/:id/cost` | 否 | 只按当前基础数据重算参考价 |
| 报价覆盖试算 | `/api/recipes/:id/cost-preview` | 否 | 只按配方快照和覆盖项试算 |
| 客户新增/修改/删除 | `/api/customers`、`/api/customers/:id` | 是 | 客户档案和默认利润率 |
| 报价新增/修改/删除 | `/api/quotations`、`/api/quotations/:id` | 是 | 报价头、状态、明细 JSON、总成本和总报价 |
| 订单采购计划 | `/api/orders/purchase-plan` | 否 | 只生成采购清单和待办草稿 |
| 活动订单准备总览 | `/api/orders/readiness-overview` | 否 | 一次平衡全部活动订单库存，汇总准备结论、问题和下一步 |
| 订单生产准备检查 | `/api/orders/:id/readiness` | 否 | 只读核对订单、BOM、零件、线圈、采购和成本价格 |
| 订单准备处理方案 | `/api/orders/:id/readiness-plan` | 否 | 将检查问题转换为有依赖顺序的确认、人工和等待步骤 |
| 订单方案动作执行 | `/api/orders/:id/readiness-actions/:actionId` | 是 | 用户确认后实时重验，只执行当前可确认步骤并返回新方案 |
| 订单新增/修改/删除 | `/api/orders`、`/api/orders/:id` | 是 | 订单头、明细、锁定成本、售价、采购清单、待办和状态 |
| 采购中心整项下单 | `/api/orders/purchase-items/batch` | 是 | 更新活动订单采购项的下单数量；不入库 |
| 采购进度与分批入库 | `/api/orders/:id/purchase-items/progress` | 是 | 更新下单/到货/入库数量；仅入库增量在同一事务内增加库存 |
| 一次性全部入库 | `/api/orders/:id/complete-purchase` | 是 | 把剩余计划登记为下单、到货和入库，并进入采购完成 |
| 配方库存状态 | `/api/recipes/:id/inventory-status` | 否 | 普通配件读取零件库，线圈转子读取独立线圈库存；只返回当前库存和状态 |
| 转子出图 | `/api/rotor/draw`、`/api/rotor/chat` | 是 | 写入出图任务和历史记录 |
| 转子参数暂存 | `/api/rotor/save` | 是 | 保存 `status=saved` 的历史记录 |

## 4. 成本快照规则

成本分三类，业务实现和页面展示都不能混用：

| 成本类型 | 生成时机 | 允许变化 | 用途 |
|---|---|---|---|
| 当前重算参考 | 查看或手动试算时 | 会随零件、线圈、铜价、设置变化 | 风险提示、人工复核、AI 查询 |
| 配方保存快照 | 新建或修改配方保存前 | 保存后不自动变 | 配方详情、报价默认基线、订单来源 |
| 订单锁定成本 | 创建订单、报价转订单或追加订单明细时 | 保存后不自动变 | 订单利润、历史追溯、采购和生产依据 |

约束：

- 配方保存必须通过 `POST /api/recipes/cost-draft` 生成保存快照。
- 配方保存 payload 和正式写入口必须检查完整 BOM；任一项目的快照单价缺失、无效或小于等于 0 时阻止保存，并提示先补齐零件型号和单价。
- 报价覆盖必须通过 `POST /api/recipes/:id/cost-preview` 试算。
- 报价转订单必须保存展开后的 BOM 快照，不能只保存 overrides。
- 订单创建和追加明细优先使用配方 `savedTotalCost`；没有保存成本时才允许回退当前重算参考。
- 前端可以有展示级预览，但正式保存、报价和订单不得使用前端自算成本作为权威值。

## 5. 报价流程

1. 选择客户，带入客户默认利润率。
2. 选择基础配方，读取配方保存快照作为默认成本基线。
3. 客户只可覆盖是否带浮球、电缆米数、外包装（牛皮纸箱/彩印箱/木箱）、泡沫型号和是否含珍珠棉；线圈直径、材质、槽眼、片数和线径沿用配方。
4. 覆盖项通过 `POST /api/recipes/:id/cost-preview` 试算。
5. 报价保存时后端重新试算，并把完整 `bomSnapshot`、`costSnapshot`、覆盖参数、单位成本和售价写入 `quotations.itemsJson`。
6. “报价中”超过一个月会在读取列表时自动标记为“已过时”。

禁止事项：

- 报价覆盖不得修改原配方。
- 报价保存不得只保存 UI 临时状态，必须能从 `itemsJson` 复原明细。
- 报价转订单不得复用未展开的 overrides 作为订单 BOM。

## 6. 订单流程

### 6.1 直接创建订单

1. 填写客户、合同号和备注。
2. 添加一个或多个配方明细。
3. 每个明细写入配方名、规格、数量、单位成本、利润率、单位出厂价和 BOM 快照。
4. 调用 `POST /api/orders/save-payload-draft` 生成保存 payload，后端会生成采购清单和待办草稿。
5. 保存订单，初始状态为 `待确认`；人工确认后进入采购流程。

### 6.2 报价转订单

1. 从报价明细读取客户、数量、报价单价和保存时已经展开的 BOM/成本快照。
2. 调用 `POST /api/quotations/:id/order-draft` 预览订单及采购计划。
3. 确认后调用 `POST /api/quotations/:id/convert`。
4. 后端在同一事务内创建订单、保存报价与订单关联并把报价更新为 `已转订单`。
5. 同一报价重复转单返回 409；转单后不允许再修改报价明细。

### 6.3 订单状态

| 状态 | 含义 | 典型触发 |
|---|---|---|
| 待确认 | 直接创建后尚未确认核心明细 | 新建订单 |
| 待采购 | 已确认，尚未登记下单 | 确认订单 |
| 采购中 | 已有下单、到货或部分入库 | 数量进度自动推导 |
| 采购完成 | 全部计划数量已入库，但订单尚未关闭 | 数量进度自动推导 |
| 已关闭 | 业务事项已结束 | 采购完成后人工关闭 |
| 已取消 | 订单不再继续执行 | 待确认/待采购/采购中填写原因后取消 |

订单状态不能任意倒退。采购中和采购完成不能手工指定；已关闭、已取消为终态。报价转订单生成的订单已经经过客户确认，因此直接进入待采购。

## 7. 采购与库存流程

### 7.1 采购清单生成

- 输入为订单明细的 `partsJson × qty`。
- “外包装估算”等成本占位项不进入正式采购清单；订单确认前必须改为零件库中具体的外包装型号和供应商，否则生产准备检查返回数据阻塞。
- 真实零件优先按 `partId` 识别，兼容数据按“型号 + 供应商”聚合，不能只按型号合并。
- 线圈转子不进入零件库；精确匹配规格、片数、材质和槽眼的正式方案按 `coilId` 识别并以“套”为库存单位。
- 插值或外推得到但没有正式方案的线圈为非库存计算项，不伪造 `partId/coilId`。
- 全部活动订单按创建顺序共享库存，前序订单占用后，后序订单只使用剩余库存，避免同一库存重复分配。
- 采购中心汇总平衡后的 `needToBuy`。
- 参数化长螺丝可以借用基础螺丝供应商，但不能扣基础螺丝库存，也不能把基础螺丝 `partId` 写给目标长度采购项。

### 7.2 采购中心

- 采购中心只聚合未完成订单的采购需求。
- 采购中心汇总 `plannedQty/orderedQty/receivedQty/stockedQty`，可按供应商和型号执行整项下单，不增加库存。
- 部分下单、实际采购价、实际供应商、到货和入库数量在订单详情逐项登记。

### 7.3 入库

- 入库发生在订单详情确认。
- 数量必须满足 `stockedQty ≤ receivedQty ≤ orderedQty`；`orderedQty` 超过 `plannedQty` 时必须明确确认超采。
- 每次提高 `stockedQty` 都只把增量加入库存，并在同一事务内记录 `stockInHistory` 批次。
- 普通零件入库前必须存在对应 `partId`，线圈转子入库前必须存在对应 `coilId`；任一校验失败时采购进度和库存一起回滚。
- 线圈采购入库增加 `coils.stock` 并写入 `coil_stock_movements`，订单号保存在流水引用中。
- 全部计划数量入库后自动进入采购完成；订单关闭是后续独立人工动作。
- `POST /api/orders/:id/complete-purchase` 是兼容的一键动作，用于确认全部剩余物料已经到货并入库，不直接关闭订单。
- 一键入库确认必须同时展示普通零件、正式线圈和非库存计算项；只有普通零件与正式线圈会增加库存，非库存项只完成采购进度。
- 采购入库只记录新到物料。系统不恢复生产执行模块，也不在订单关闭时自动扣料；实际领用由仓库分别通过零件库存调整和线圈库存调整登记出库。

### 7.4 配方库存查看

- 配方详情通过 `GET /api/recipes/:id/inventory-status` 读取配件与线圈库存；线圈转子不依赖零件库。
- 按 `model + supplier` 精确匹配，必要时回退同型号。

### 7.5 订单生产准备检查

- `GET /api/orders/:id/readiness` 复用全部活动订单按顺序共享库存的计划结果，不建立第二套库存计算口径。
- 检查顺序固定为订单状态、配方与BOM、零件库存、线圈库存、采购进度、成本与价格。
- 当前可用库存覆盖需求时才可判定可生产；已下单、已到货但未入库仍属于待补料。
- 没有正式库存方案的计算型线圈、未绑定具体型号的外包装估算、没有零件库存映射的采购项、缺BOM或未确认订单返回数据阻塞。
- 库存满足但成本缺失、售价低于成本或来源配方不可追溯时返回待复核，不把商业风险伪装成物理缺料。
- 检查只给出结论、证据和建议入口，不确认订单、不自动采购、不调整库存。
- 页面只展示物料、库存和状态，不提供生产数量、生产确认或自动扣库存操作。
- 缺货、零件未建档和正式线圈方案缺失必须明确标记。

### 7.6 订单准备处理方案

- `GET /api/orders/:id/readiness-plan` 先执行同一套生产准备检查，再按数据修复、订单确认、采购下单、到货和入库依赖生成步骤。
- `confirmable` 步骤只携带未来确认所需的标准工具名称和参数，不在方案接口中执行；`manual`、`needs_input`、`monitor` 分别表示人工处理、等待业务决定和外部状态跟进。
- 缺BOM、普通物料未关联零件、计算型线圈没有正式库存方案时，确认订单和采购步骤必须等待这些前置项完成。
- `/api/orders/lookup` 专供只读解析订单ID、客户名称和合同号，不调用会刷新采购缺口的订单列表接口。
- 本阶段仍不引入生产数量、生产确认、自动扣库存或独立生产执行模块。

### 7.7 订单方案动作执行

- AI 收到“执行第几步”后先刷新处理方案，不根据旧会话中的步骤状态直接写入。
- `execute_order_readiness_action` 是受确认保护的写工具；只有确认卡片批准后才调用订单标准动作接口。
- 服务端再次生成实时检查和方案，只允许白名单中仍为 `confirmable + available` 的动作；步骤已完成、已变化或受阻时返回 `409`。
- 当前自动动作限于确认订单并按实时进度进入采购流程、生成采购清单。人工修正BOM、补价格、采购下单、到货和入库仍走现有业务页面和标准接口。
- 执行结果返回更新后的订单和 `nextPlan`，AI 展示新的剩余步骤，形成“检查、计划、确认、执行、复查”闭环。

### 7.8 活动订单准备总览

- `GET /api/orders/readiness-overview` 只读取未关闭且未取消的订单，一次生成全部订单共享库存的平衡计划，再复用单订单检查和处理方案服务。
- 总览按数据阻塞、待补料、待复核、可生产排序；汇总数量与订单明细来自同一次计算，避免看板和 AI 使用不同口径。
- 每条订单明细只保留主要阻塞、风险、缺料和第一个未阻塞步骤，供管理看板快速判断；需要完整六步依据时仍读取单订单检查。
- `get_order_readiness_overview` 和管理看板“订单准备”页签均调用该只读接口，不确认订单、不更新采购、不调整库存，也不引入生产执行模块。

### 7.9 重点订单处理工作台

- 管理看板总览使用 `/orders?orderId=:id&view=readiness` 进入指定订单，不再只跳转到订单列表。
- 订单页面读取 `orderId` 后从标准订单列表定位订单，并按 `view` 恢复客户要求、生产准备、型号、采购或待办页签；关闭详情时清除 URL 中的订单上下文。
- “生产准备”页签并行读取 `/api/orders/:id/readiness` 和 `/api/orders/:id/readiness-plan`，展示完整检查依据、问题、缺料和依赖步骤；刷新只重新读取实时结论。
- 该页签不直接执行方案工具。订单确认、采购进度、入库、关闭和取消仍通过订单详情现有明确按钮和标准写接口完成。

### 7.10 订单页面上下文 AI

- 打开订单详情或切换客户要求、生产准备、执行档案、型号、采购、待办页签时，前端同步更新 URL，并把订单 ID 与当前页签作为独立 `pageContext` 传给右侧 AI。
- 页面上下文不进入用户消息或会话历史，只用于解析“这个订单”“它”“下一步怎么处理”等省略指代；明确订单编号和全部订单问题不会被当前页面覆盖。
- 后端只接受订单类型、正整数 ID 和白名单页签，不接收客户端标签、提示词、状态、金额或库存等业务事实。
- 解析后的问题仍先执行实时订单详情、生产准备检查或处理方案工具，页面上下文不能替代标准 API，也不会扩大 AI 写权限。

### 7.11 客户要求与确认知识

- 订单“客户要求”页签通过统一文件接口上传生产要求、包装要求、客户图片、Excel 或 PDF，并以 `order + customer_requirement` 关系保存；原文件只保存一份。
- “AI 归纳”在订单页面直接调用统一 AI 流式接口，并把结果原地填入客户要求编辑框，不跳转工作台、不要求复制粘贴。AI 只按附件原文生成分类草稿，把缺失和冲突内容列为待确认，不得把经验推断写成客户要求。
- AI 先展示归纳结果；只有用户明确要求保存时，`save_order_requirement_draft` 才生成确认卡片并调用草稿接口。AI 无权确认知识或撤销确认。
- 订单页面可以编辑归纳、选择本次依据文件并保存草稿。点击“确认进入知识库”后，最后确认版本合并到现有订单知识条目，自动刷新检索；原始附件本身不会仅因上传而被当作已确认事实。
- 已确认后继续编辑只产生待确认草稿，知识库继续使用上次确认版本，避免半成品覆盖正式知识。重新确认后替换；撤销确认后知识库移除客户要求，但草稿和原文件保留。
- 客户要求归档不修改订单产品、配方、采购或库存，也不恢复生产执行模块。后续生产资源和过程追溯基于确认知识继续扩展。

### 7.12 订单执行事实档案

- 订单“执行档案”页签使用多条时间线记录生产前资源与物料准备、生产中产能或供应商调整和过程异常、生产后质量与交付结果，不把全部过程压成一段不可追溯说明。
- 每条记录保存阶段、事实类型、标题、发生时间、事实说明和依据附件。附件复用统一订单文件对象，以 `execution_evidence` 区别客户原始要求，不复制原文件。
- 执行依据附件的“AI 归纳”同样原地填入当前事实说明，用户继续核对阶段、类型和正文；该动作只生成页面草稿，不自动调用保存或知识确认接口。
- 草稿可以反复修改或删除；人工点击“确认进入知识库”后，确认快照才合并到现有订单知识条目。修改草稿时旧确认事实继续可检索，重新确认才替换。
- 已确认记录引用的附件不能直接解除订单关联；先撤销确认，或重新确认一版不再引用该文件的内容。撤销后草稿和附件仍保留。
- `save_order_execution_draft` 只在用户明确要求保存已发生事实时生成确认卡片并新建草稿。AI 无权确认、撤销或删除正式事实。
- 执行档案只负责记录与追溯，不修改订单状态、配方、采购或库存，也不恢复已经取消的生产执行模块。生产准备页继续承载实时检查、方案和待办，两者不得混写。

### 7.13 只读订单知识包

- `GET /api/orders/:id/knowledge-package` 统一返回实时订单、采购、待办、生产准备和处理方案，以及最后一次人工确认的客户要求、执行事实和来源文件。
- 实时业务数据每次请求重新读取和计算，不依赖知识库同步；确认事实只读取 `confirmed_*` 快照，未确认草稿只计入待确认数量，不作为正文依据。
- AI 工具 `get_order_knowledge_package` 用于客户要求、历史调整、过程异常、质量和交付追溯。客户名或合同号匹配多张订单时必须要求用户明确，不能猜选。
- 知识包只读，不确认事实、不执行生产、不修改订单、配方、采购或库存。系统没有确认记录时必须明确回答“未记录”。

### 7.14 统一管理待办中心

- `GET /api/workbench/action-center` 实时汇总订单准备、经营风险、数据质量、规则学习和知识库健康五类现有检查，不建立第二套业务判断规则。
- 待办按严重、较高、中等、较低优先级排序；同一订单的采购缺口由订单准备检查统一呈现，避免重复提醒。
- 每条待办提供来源、建议动作和对应业务页面入口。看板与 AI 使用同一结果，AI 可回答“今天最先需要处理什么”；当前单人管理场景不要求分配负责人或维护团队任务状态。
- 待办中心只读，不确认订单、不修改配方、不审核规则、不执行知识同步；处理动作继续在对应页面通过既有权限和确认流程完成。
- V7.1 后台每 5 分钟核对一次稳定待办键，记录首次出现、当前连续出现起点、消失时间和累计出现次数；普通打开看板不会触发写库。
- `management_action_events` 只追加出现、消失和再次出现事件。事项消失仅表示实时检查当前不再检出，不能推断是谁处理或为什么解决。
- 看板在当前待办旁显示持续时间和第几次出现，并展示最近消失记录；AI 只读使用同一生命周期信息。
- V7.2 从完整待办中自动选出最多 3 项“今日执行队列”。业务优先级始终优先，同级再比较持续时间、重复出现次数和影响数量，并显示每项排序依据。
- 今日执行队列只减少判断步骤，不隐藏其他待办、不建立负责人或手工状态；处理仍直达原业务页面，实时检查不再检出后由 V7.1 自动记录消失。
- V7.3 为每项队列返回统一处理路径：打开业务页面、需要业务判断、等待外部变化或 AI 可确认。看板显示下一步和完成标准，避免用户重新分析从哪里开始。
- 只有当前订单方案明确允许的“确认订单”和“生成采购清单”可交给 AI；点击后 AI 工作台预填处理请求，仍先刷新今日队列和订单方案，再展示确认卡片。其他事项不会因为进入执行队列而获得写权限。
- V7.4 在零件、配方、模板、订单、线圈、客户、报价、质量规则和知识库等核心业务写入成功后触发短延迟复查；连续操作自动合并，失败响应、只读查看、草稿和试算不触发。
- 复查后不再出现的事项自动转为已解决并进入归档记录，不要求人工勾选完成。归档只说明当前实时规则不再检出，保留首次出现、持续时间和再次出现事件。
- 看板和 AI 共用最近 24 小时处理进展，分别汇总自动归档、仍待处理、暂时受阻和反复出现；AI 不从会话历史猜测完成情况。

## 8. 知识库与 AI 会话

- `knowledge_entries` 是由正式业务数据生成的派生索引，不是新的业务事实来源。
- 同步按 `sourceTable + sourceId` 增量更新，原始数据失效时移除对应条目，并保留未变化条目的稳定 ID。
- 核心业务通过标准写入 helper 变更后自动提交知识刷新；连续写入短延迟合并，失败自动重试，人工同步只作为全量核对和恢复兜底。
- 自动、即时和人工同步的成功、失败及每次重试都会写入 `knowledge_sync_runs`；看板读取最近历史用于定位异常，记录最多保留 200 次。
- 健康检查只在自动同步关闭、等待或运行超时、未安排变化和失败未恢复时告警；没有业务变化不会因时间间隔产生假告警。人工恢复仍先确认再同步。
- FTS 与知识条目在同一事务内刷新；同步失败时保留上一版完整索引。
- AI 搜索结果必须能返回原始来源类型和来源 ID，业务判断仍以原资源 API 为准。
- 系统外技术说明、文本、Excel、测试报告和 PDF 原件保存在 `knowledge_documents`，通过 `document` 知识条目进入现有检索；文本和 Excel 可检索提取正文，PDF 当前只使用人工填写的标题、说明和标签，不得推断未解析的图纸内容。
- 配方智能检查的学习反馈绑定当时的泵壳模板和配方版本；内容修改或模板变化后，旧反馈停止影响规则并进入待重新检查队列。
- 归档带有学习反馈的配方时，同一事务会立即刷新候选规则和已批准规则知识；归档证据只保留历史追溯，不再支持当前规则。
- 学习证据健康检查覆盖尚未形成候选规则的单条反馈，只提供复核队列，不自动恢复反馈、修改配方或批准规则。
- 数据质量看板的待复核反馈可按配方逐条打开，配方页会自动执行一次智能检查；用户根据当前配置重新确认对应提醒后，该反馈才重新成为有效学习证据。
- 原提醒重新出现时，页面会精确高亮并要求按当前配置重新判断；原提醒已经消失时，可确认已解决并将旧判断恢复为中性复核状态。服务端会再次执行当前配方智能检查，防止绕过页面误清理仍存在的提醒；该动作保留原始证据，不删除历史，也不会修改配方。
- 待复核任务按配方聚合；同一配方的多条反馈一次打开后按进度逐条处理，完成当前反馈后自动定位下一条，但每条仍需独立保存人工判断。
- 每次复核保存后展示规则学习刷新结果；暂时跳过只改变当前页面的处理顺序，不改变反馈状态。整组完成后清理复核参数，返回数据质量看板时重新读取健康队列。
- AI 会话完整保存在 SQLite；发送给模型的上下文只保留最近 10 条用户或助手消息。
- 历史会话中的写操作结果只用于回看，不能再次直接确认执行。

## 9. 允许调整的内容

可以调整：

- 页面布局、弹窗、步骤条、表格和筛选交互。
- 页面状态和资源缓存组织方式。
- API client 内部封装。
- 业务 helper 的文件结构。
- UI 组件库和动效实现。

必须保持不变：

- API 标准契约和路径。
- 写库点。
- 成本快照生成时机。
- 报价转订单保存展开 BOM 快照。
- 采购中心不入库。
- 入库通过订单业务动作 API；配方库存视图保持只读，零件与线圈分别使用自己的库存调整入口。

## 10. 开发检查清单

新增或调整业务功能时必须同步遵守：

- [前端状态边界](./frontend-state-boundary.md)：约束远端数据、页面本地状态、跨资源刷新和派生数据位置。
- [UI/交互约束](./ui-refactor-guidelines.md)：约束页面结构、动效、表单、表格和组件风格。

- 新页面是否只通过标准 API 入口写库。
- 保存动作是否明确调用后端权威成本接口。
- 只读预览是否没有写库副作用。
- 写操作后是否重新拉取对应资源。
- 新增 API 是否已同步 `docs/api-reference.md` 和 `docs/api-sop.md` 约束。
- 新增业务规则是否有 helper 或服务层测试，而不是只藏在页面组件里。
