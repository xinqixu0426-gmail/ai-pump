## 0. 一句话现状

系统是一个已上线的水泵工厂管理与成本核算系统，内嵌一个只读 AI 助手（外部 Agent 也可经 MCP 调用）。
过去一段时间的投入主要建在一条叫 **ontology** 的链上：它建成了 **12 条「谁引用谁」的结构关系**、
一套规范化绑定与遍历、以及一个**只覆盖「线圈↔配方」一个关系族**的软件预排读取路由。
**该路由在生产上从未接管任何请求（开关默认关闭）**；真正留在生产里生效的只有一件能力
（按编号反查「这个线圈被哪些配方用」）。

而用户可感知的痛点集中在**语义与确定性**（同一个规格片数有多套方案只报一套、口语叫法解析不了、
金额口径说不清、参数不清时替用户猜），**这些都不在关系结构这一维度里**。
（分析）因此"没有明显感觉"的原因不是 ontology 走得不深，而是**最初的投入维度与痛点的维度不同**。

## 2. ontology 这条链实际建了什么（事实）

### 2.1 模块清单

`api/ontology/` 共 **20 个文件**：`contract.cjs`、`validator.cjs`、`sources.cjs`、`relationBinder.cjs`、
`bindingContract.cjs`、`bindingMetadata.cjs`、`bindingCurrentFacts.cjs`、`resolver.cjs`、`resolverContract.cjs`、
`traversal.cjs`、`traversalBinder.cjs`、`traversalContract.cjs`、`traversalPolicy.cjs`、`traversalShadow.cjs`、
`traversalWorker.cjs`、`shadowContract.cjs`、`shadowEligibility.cjs`、`shadowWorker.cjs`、`runtimeShadow.cjs`、
`relationRoutingCanary.cjs`。

### 2.2 关系契约：12 条关系，全部是结构关系

| 关系 | 方向 | authority | 类型对 |
|---|---|---|---|
| `recipe.uses_template` / `template.used_by_recipe` | 正/反 | CANONICAL_DIRECT | recipe ↔ template |
| `recipe.uses_coil` / `coil.used_by_recipe` | 正/反 | CANONICAL_DIRECT | recipe ↔ coil |
| `order.belongs_to_customer` / `customer.has_order` | 正/反 | CANONICAL_DIRECT | order ↔ customer |
| `quotation.belongs_to_customer` / `customer.has_quotation` | 正/反 | CANONICAL_DIRECT | quotation ↔ customer |
| `order.contains_recipe` / `recipe.contained_in_order` | 正/反 | DETERMINISTIC_DERIVED | order ↔ recipe |
| `recipe.contains_part` / `part.contained_in_recipe` | 正/反 | DETERMINISTIC_DERIVED | recipe ↔ part |

契约里另有明确 **EXCLUDED** 的候选（如 `order.lines` 快照序号、`parts.stock` 过滤集合、`part.facts` 标量事实），
理由是它们不是实体到实体的关系。

**这 12 条全部回答"谁引用谁"**：没有任何一条描述业务规则、口径、算法或歧义处理。

### 2.3 接进回答链的只有 2 个模块，且都在关闭的开关后面

全仓库只有两处 `require('../ontology/...')`：

| 位置 | 模块 | 开关 | 生产取值 |
|---|---|---|---|
| `api/services/aiAssistantRuntime.cjs`（约 332 行） | `relationRoutingCanary.cjs`（路由） | `AI_ONTOLOGY_RELATION_ROUTING_CANARY_ENABLED` | **未设置（关闭）** |
| `api/services/aiAssistantRuntime.cjs`（约 765 行） | `runtimeShadow.cjs`（只写观测） | `AI_ONTOLOGY_RELATION_SHADOW_ENABLED` | **未设置（关闭）** |

生产复核：`.env` 无任何 ONTOLOGY 行；`runtime_settings` / `system_settings` 无 ONTOLOGY 键；
LaunchDaemon 注入环境只有 `NODE_ENV` / `PATH` / `XPC_SERVICE_NAME`；运行进程环境无 ONTOLOGY 变量；
生产日志中 `ontology` 出现 **0** 次。→ **生产上 ontology 路由代码根本不加载。**

### 2.4 路由能力本身的范围（若打开会怎样）

- **只覆盖一个关系族**：`recipe ↔ coil`；且只处理语义类 **PURE_RELATION_QUERY**（纯粹问关系）。
  成本、库存、对比、配置、写命令等**被明确排除**。
- 准入还需要：P4 规范化绑定为 BOUND（唯一 canonical 根 + 方向）、provider 模式在
  `['local','local-first','deepseek']` 内、所需工具已在目录中。
- 命中后由**软件**在首次模型调用前排定必需读取，模型只负责把已取得的结果合成回答。
- 门禁要求：canary ON 与 OFF 的最终回答**逐字相同**、provider 调用数**不得增加**、无错误 root/relation/direction。
- 文档已明确一条口径修正：**canary=false ≠ 零行为变化**——这一版本新增的"有界反查"能力即使路由关闭，
  legacy 路径也能使用。

### 2.5 生产上真正生效的 ontology 时代能力（事实）

| 能力 | 说明 | 生产证据 |
|---|---|---|
| `get_recipes_by_coil`（有界规范反查） | 从 `recipes.coil_id` 外键按键集分页读"引用该线圈的配方"，返回集合完整性语义（`complete` / `unconfirmedLegacyReferences`） | 生产会话 58（msg 330/331）：问「使用12-120线圈做的配方有哪些」→ 调用 `search_coils` + `get_recipes_by_coil`，回答含"反查结果为完整集合（complete=true）" |
| P8L 有界 legacy 关系修复 | 不再要求读取完整配方聚合（旧实现在真实库上该工具结果 120,990 字节，超过单次 96 KB 上限，模型只拿到截断目录） | 代码与门禁在库；该缺陷是**生产发现的，不是门禁发现的** |

### 2.6 覆盖率实测（这决定收益上限）

| 指标 | 数值 |
|---|---|
| 用户消息中属于"线圈/定子 ↔ 配方/成品"关系问法 | **2 / 172 ≈ 1.2%** |
| 助手轮次中真正调用过 `get_recipes_by_coil` | **1** |
| 其余绝大多数问法 | 成本、单价、测试报告、订单详情、配方/线圈清单（例如 `12-120的成本是多少`、`202和203轴承的价格是多少`、`我要找V550的`） |

## 3. 现在真正决定回答质量的链路（事实）

AI 请求入口：`POST /api/ai/chat`（页面与脚本）与 `/mcp`（外部 Agent）。
调度：`api/services/aiDispatcherV3.cjs` → 普通只读问答走 `aiAssistantRuntime.cjs`，
明确业务写命令走受保护的 `aiAgentRuntimeV3.cjs`（写操作需人工确认）。

`aiAssistantRuntime` 是一条**模型驱动**的工具循环（无独立意图规划器），关键层次：

| 层 | 文件 | 作用 |
|---|---|---|
| 资源解析 | `api/services/aiResourceResolutionV3.cjs` | 名称/简称解析；区分「不存在」与「多候选」；剥离口语助词；判定"变更描述不是名称" |
| 依据校验 | `api/services/aiToolIdentifierGrounding.cjs` | 阻止模型自造**数字**（片数/线径/机筒长度…）与**身份字符串**（材质/槽眼）；口语简写归一 |
| 执行器 | `api/routes/ai/executors/*.cjs` | 每个工具对应一个执行器，只调用正式 API；结果形状与提示在这一层确定（内置 AI 与 MCP **共用**） |
| 证据 | `api/services/aiExecutionEvidence.cjs` | 每个结果带正式 API 调用证据；"已核实缺失/空结果"必须可证明 |
| 回答守卫 | `api/services/aiAssistantAnswer.cjs`（受冻结保护，不许改） | 金额来源校验、正式金额表、缺失目标、空结果措辞 |
| 回答后处理链 | `aiAssistantRuntime.cjs` 末尾 | 依次：安全知识回答 → 补线圈身份 → 补技术档案结论 → 本地裁剪 → **补跨目录候选** → **补多方案清单** → **规矩册口径** → 展示层兜底 |
| 展示 | `api/services/aiResponsePresenter.cjs`（受冻结保护） | 必答字段兜底 |

**今天所有让用户有感的变化都发生在三处：执行器结果形状、依据校验、回答后处理链。**
（分析）这三处才是当前"AI 聪不聪明"的实际杠杆点，而 ontology 的 12 条关系不在这条链的任何一环上。

## 4. 业务规矩册现状（事实）

`docs/ai-business-rulebook.md`：**19 条规矩**，逐条标注执行状态。

| 状态 | 数量 | 含义 |
|---|---|---|
| **已强制** | 13 | 系统保证，有代码 + 测试，不靠模型自觉 |
| **仅提示** | 5 | 只写在提示词里，模型可能记得也可能忘（回答波动来源） |
| **未支持** | 1 | 系统做不到，必须如实说明，不许编数 |

已强制（13）：成本口径必须标明（整机 vs 线圈）、同一规格片数多方案必须全说、泵壳本体成本需机筒长度、
假设价格必须说明口径、历史值不能当当前值、口语助词不是名称、变更描述不是名称、跨目录必须查全、
材质槽眼必须来自用户输入或本轮正式结果、金额格式不得顶掉结论、无依据金额必须拦截、
确认不存在要说清并列出已核实范围、配置未定价不得说成完整成本。

仅提示（5）：四种成本不能混说、换配置重算的继承规则、参数不清不许猜（多候选澄清）、
历史叫法/改名别名对齐、多个默认不许替用户选。

未支持（1）：**线圈级"按指定铜价算"**——服务端 `api/services/coilCost.cjs` 已支持 `copperPrice` 参数，
但 AI 工具 schema 未开放；整机级（配方/BOM）完全不支持。

报告同时登记了 **2 处"已知补丁"（还没换成规则）**：
① 判断"变更描述 vs 名称"仍靠关键词表（每发现一种新说法就要加词）；
② 金额证据校验对**派生数字**（两个正式金额相减）偏严，会拦下解释性正文。

### 5.3 上游判据现状：哪些已经是"规则"，哪些还是"补丁"（分析）

判断标准：换一个用户没提过的说法是否也成立。

**已是规则**：口语助词剥离、变更描述≠名称（配方/模板两条路径）、跨目录查全（任何目录 + 两种失败形态）、
同一规格片数多方案披露（执行器 + 回答层，内置 AI 与 MCP 共用）、金额格式不得顶掉结论、
材质/槽眼依据校验（必须来自用户输入或本轮正式结果）、假设价格与成本口径说明。

**仍是补丁**：
- "变更描述 vs 名称"的**关键词表**（换成/整机/库存/明细/成本/价格…）。根因是名字识别的判定不是结构性的；
  真正的规则应是"名称字段必须能被正式目录解析，否则说明它不是名称"，或按句式/长度判定。
- 金额证据对派生数字偏严 → 导致解释性正文被丢弃。

## 7. 已确认的结构性发现（分析，供评审者判断）

1. **投入维度与痛点维度不同**：建的是"谁引用谁"（结构）；用户痛点是叫法/口径/歧义/参数缺失（语义与确定性）。
2. **关系网在现有数据上近乎空转**：1 条配方、0 张订单；关系遍历没有内容可走，收益无法体现。
3. **路由开关关闭 → 设计收益（软件预排读取、不依赖模型自觉）从未在生产出现**；
   用户能感觉到的只有这一版新增的"能力"（有界反查），不是路由。
4. **同一时期还加了约束而没有加能力**（金额证据、缺失目标、澄清机制），所以体感更接近"变笨、更啰嗦"。
   用户原话："有些地方还不如我之前的执行链"。
5. **覆盖率决定上限**：ontology 路由的目标问法占真实提问约 **1%**；而成本/价格/身份类占约 **98%**。
6. **验收环境与生产环境不一致**，导致门禁通过不能代表生产可用（4 配方 fixture 的教训）。

## 8. 不可破坏的约束（事实性约束，计划必须满足）

1. **这是正在使用的工厂成本系统**：金额错误比回答啰嗦严重得多；现有安全不变量必须保留——

4. **ontology 冻结语料与 oracle v1/v2 不得改写**，只能新增版本（v3）并同步调整门禁断言。

6. **外部通道可去可留**：用户明确表示"如果 ontology 能用，可能弃用 MCP"；MCP 生产验收当前停用。
   计划不应把 MCP 当作必需依赖。
7. **数据不可随意造**：生产库是真实业务账；需要测试数据时应使用**副本**，不得污染生产。
