# 原 AI 调度的查询限制审核

日期：2026-09-07。范围：审核原生产 V3 与保留的本地 V3/V4 调用链，细化新版私人助理设计。本次不修改调度源码、生产配置、业务权限或数据库。

## 结论

原调度确有多处把“当前查询策略”变成“模型不能跨越的执行限制”。单人助理应让全部已登记业务只读能力可发现、可调用，允许查目录、跨域找对象、查关联和总览，再根据结果选择下一步；不需要把这些查询按身份或首轮分类分配权限。

正式业务事实仍由 API 提供，业务写入在本人确认后执行。工具 schema、有效资源、分页和取消是正确性及运行控制，不等于把问题分成越来越窄的许可类别。

## 纯函数检查

直接调用现有目录/恢复函数，结果保存在 `output/framework-retirement/dispatcher-audit-probes.json`：

1. single 查询目录不包含 `get_order_readiness_overview`，global 查询目录包含它。
2. conversation 模式工具目录为空。
3. 以 `preview_recipe_cost` 为原计划，coil 类型不能通过 `recoveryTargetCompatible`。
4. 以 `calculate_coil_cost` 为原计划，同样的 coil 类型可以通过。

这些检查没有调用模型、生产 API 或写数据库。它们证明限制条件确实存在，不证明用户过去“12-200”的每次失败都由同一条件引起；该问题的完整运行归因仍需新版实施时以固定场景收集真实工具轨迹。

也不能把所有旧保护都说成错误。例如禁止把明确指定的配方替换成相似线圈、要求真实 API 事实、确认后才写入，均应保留。需要删除的是把原计划假设固化成不可变业务范围，以及多条重复运行/恢复链。

## 新版权限与行为

- 已登记业务只读 Query 和无副作用 Preview 默认可发现、可调用，覆盖客户、零件、线圈、配方、报价、订单、采购、库存、资料和知识库。
- 可以先查再问、跨领域搜索、读取关联/汇总、调整搜索参数、并行独立查询、比较多个对象。只有歧义确实影响目标时才让用户选择。
- 能力目录的相关性排序只是效率优化，不能以 single/global、原业务域或原计划步骤拒绝合理的只读调用。
- 业务变更可以主动准备、补齐信息和展示正式预览，执行沿用本人确认；不再增加 owner 专属目录或按实体审批的权限层。
- 个人记忆的明确自然语言保存/更新/删除是用户授权，不再额外要求点提交。记忆内容须来自用户明确要求，不能由资料中的指令触发保存。
- 失败只影响依赖该失败的结论；已确认的事实可以回答。价格、成本和库存数值仍来自正式服务，不把“有工具使用权”当作可以编造结果。

## 验收重点

第一批就验证成本、自然语言记忆、跨会话调用和配方比较的完整使用闭环。随后覆盖：单对象问题使用集合能力辅助调查、先搜配方未果后发现线圈并澄清、先查订单再查采购/库存、查到一项而另一项失败时保留可靠结果、修改记忆后旧解释失效、用一句“记入长期记忆”完成保存，以及本人确认前业务零写入。

完成标准以实际业务任务和必要提问次数为主，不再以通过多少内部分类/证据阶段作为“聪明”的替代指标。初次真实验收保留全部失败，发现可复现问题后修复共同原因；不靠扩大白名单中的具体问句或反复重跑至全绿收尾。
