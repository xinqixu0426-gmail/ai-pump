# AI 纠错学习与发布回归使用报告

> 核对日期：2026-09-07。本文维护反馈按钮、纠错审核和回归流程；自然语言个人记忆是独立入口，见 [私人 AI 助理](ai-assistant.md)，不需要先提交反馈候选。

## 1. 解决的问题

AI 偶尔会误解工厂俗称、业务分类或操作习惯。用户指出错误后，如果只修正当前回答，
同类问题仍可能在以后或升级模型后再次出现。

当前系统把一次明确纠错拆成三层：

1. 原始反馈：保留当时的问题、回答、来源和用户填写的正确做法。
2. 长期纠正规则：只在相关问题中进入 AI 上下文，帮助 AI 按工厂习惯回答。
3. 回归用例：用确定性规则检查以后回答是否仍遵守正确做法。

长期规则负责“教会 AI”，回归用例负责“证明它没有重新犯错”。两者有关联，但职责不同。

## 2. 已实现能力

- 在 AI 回答下报告“内容错误”并填写正确做法后，同一事务生成长期规则和唯一回归候选。
- 能从明确术语、型号、数字、单位和禁止结论中生成确定性检查候选，但无论置信度高低都以 `reviewStatus=pending`、`enabled=false` 进入人工审核；只有批准且关联规则有效后才会启用。
- 只有人工批准的候选才会启用对应长期规则并可加入发布回归，系统不会把模型提炼结果自动升级为长期事实。
- 在知识库的“AI 治理”页可以查看、纳入或拒绝纠错回归用例，并查看 9 条核心系统门禁。
- 长期规则具有全局/领域/对象范围、规则类型、优先级、生效期、版本和冲突状态；管理页可以查看和编辑。
- 编辑规则正文或范围会升高版本、同步更新回归条件并重新待审；停用规则会同步停用回归，恢复规则后仍按审核状态决定是否生效。
- 真实 AI 回归使用系统当前模型、当前数据库和标准工具链，不让 AI 给自己打分。
- 最近一次内部发布门禁失败会作为稳定的“知识健康”事项进入管理看板“今日待办”；页面手动检查的历史记录不会直接阻断发布，发布时会重新执行当前核心检查，失败则阻止验收。
- Mac Mini 服务部署通过健康检查后自动执行 AI 发布门禁；9 条必须存在、启用、审核通过并开启门禁的核心系统检查，以及额外开启发布门禁的用户纠错案例都会参与。
- 外部模型流式连接瞬时中断时自动有限重试，连续 3 次不能完成才阻止验收。
- 每次门禁结果写入 `logs/ai-release-gate-latest.json`，只保存判定结果和失败依据，
  不保存完整 AI 回答。

### 2.1 持续学习闭环

系统的“越用越懂业务”采用受控闭环，而不是让模型自由改写知识：

`明确反馈 → 结构化规则候选 → 人工审核 → 范围/有效期/冲突判定 → 当前问题相关注入 → 真实 AI 复测`

- 只有用户明确选择“内容错误”、填写正确做法并勾选长期学习，系统才会创建候选；候选仍需在 AI 治理页人工批准。
- 规则按结构化业务域、对象范围和当前问题选择，不把所有历史纠错无差别塞进每次对话。
- 已批准纠错规则仍由现有规则服务加载；默认私人助理按当前问题组合只读工具，不使用旧 V3/V4 的规划、恢复图或 Evidence Ledger。
- 工具与回归规则检查正式来源、数值和错误语义；接口失败不等于资料不存在，技术失败和未完成调查不得标为通过。
- 目标测试报告不存在时，允许正式技术档案查询的负结果，或精确目标配方详情查询确认父配方不存在的等价负证据。后者必须具有原目标、recipe 类型、AI_RESOURCE_NOT_FOUND、formal_api_query_failure 及正式 GET /api/recipes 调用记录；简称、相近名称、成功详情、知识搜索和技术错误不能代替该证明。报告存在时仍核对专用工具、内容和来源，不降低原判定标准。
- 绕组档案只有一个正式方案时，身份可出现在数据之前或之后，仍须同时包含材质、槽眼和正确字段值；多个方案继续按身份分段校验，禁止跨方案借用绕组值。
- `test:ai-architecture` 与 `test:ai-shadow` 保留为旧实现诊断入口，不能证明 V1 默认助理或生产已通过验收。当前助理入口及隔离验收见 [私人 AI 助理](ai-assistant.md)。

## 3. 日常使用

### 3.1 让 AI 学习一次纠错

1. 在 AI 回答底部点击“报告问题”。
2. 选择“内容错误”。
3. 在正确做法中写清楚以后应该如何理解或执行。
4. 启用“学习这个正确做法”并提交。

正确做法应尽量明确，例如：

> “12-120”表示规格 12、定子 120 片，应查询线圈正式方案并调整线圈库存，
> 不能当作零件库型号。

不建议只写“回答错了”“以后注意”，因为这类说明无法形成可自动判定的检查条件。

### 3.2 审核纠错候选

打开“知识库 → AI 治理”。

- “已纳入”：以后每次真实 AI 回归都会检查。
- “待确认”：尚未由人工确认，不论机器提取置信度高低都不会进入 AI 运行时。
- “未纳入”：保留原始证据，但不阻止发布。
- “规则已停用”：长期规则不再进入 AI，本用例也不会执行。

长期规则卡片同时显示“已生效、待审核、待生效、已过期、有冲突、低优先级、重复、已停用”。只有相同“规则主题”和适用范围的规则才互相冲突；若不同正确做法的最高优先级相同，系统会暂停整组而不是猜测采用哪一条。在规则编辑页调整规则主题、范围、优先级或正文后重新审核。

### 3.3 手动运行检查

页面的“系统检查项管理”用于查看核心检查。迁移 72 将核心检查纳入生产发布门禁，迁移 73 会恢复旧页面曾停用的原固定核心项，迁移 76 增加模板配置成本检查，迁移 79 进一步要求该检查的最终回答明确复述 `12-120` 线圈和带浮球；9 条核心检查同时参与手动检查和生产发布门禁，普通管理接口不能停用。如果业务口径变化，应修改权威规则和确定性判定并重新验证，不能用关闭检查绕过失败。

点击“运行知识库检查”，或者在项目目录执行：

```bash
npm run test:knowledge-live
```

开发阶段定位单个失败案例时，使用普通登录身份按稳定 `case_key` 运行诊断：

```bash
npm run test:knowledge-case -- --case-key=part-current-price
```

手动全量检查和单用例诊断都使用普通登录身份，内部身份只用于正式 release。正式
release 统一写入独立的 `release:internal` namespace，发布健康只读取该 namespace，
因此升级前遗留的 `internal` 手动记录也不会继续冒充发布结果。单用例诊断只接受已审核且已启用的案例；未知、停用
或待审核 key 会明确失败。诊断运行使用独立 owner namespace，不会中止或替换页面
最近一次手动全量运行。它生成的报告会标记为 `mode=diagnostic`、
`releaseGate=false`，不能作为发布通过
证据。`release` scope 明确拒绝 `--case-key`；固定 9 个核心案例由服务端与 runner
共享同一策略并双重校验，最终发布仍必须执行全部门禁案例。运行创建后，逐项结果和
完成操作沿用同一主体访问判定：内部发布主体可继续访问 `release:internal`，普通登录
主体可继续访问自己的 manual/diagnostic namespace，其他主体按不存在处理。

页面会显示通过、需要修复、需要确认以及每一项失败依据。修改检查项配置后，旧结果会标记为“历史记录”；重新运行后才生成当前配置对应的新结果。

## 4. 发布时如何工作

普通代码验证仍使用：

```bash
npm run verify:release
```

生产服务启动并通过 API/Web 健康检查后，Mac Mini 发布脚本自动执行：

```bash
npm run verify:ai-release
```

发布门禁与页面手动运行仍是两次独立记录：清单非空时，清单要求的核心系统检查会阻止错误 AI 版本通过发布验收；已批准、已启用且打开发布门禁的用户纠错案例在此基础上继续追加。**2026-09-19 起清单显式置空**：九条旧内置核心系统检查引用的实体已随数据库清理不存在，负责人决定全部退役（迁移 86 删除用例行及其运行结果）。因此当前的 `verify:ai-release` **没有可执行用例**，报告会写成 `status=passed`、`coreCasesRetired=true` 并在 `note` 里说明"本轮不构成 AI 质量证据"——发布不再被旧用例阻断，但也不再有任何自动 AI 质量拦截。

门禁规则：

- 全部通过：本次发布可以验收。
- 任一失败：发布命令返回失败。
- 任一待确认或模型调用失败：发布命令返回失败。
- 清单非空时，清单要求的核心系统案例任一缺失、停用、待审或未进入门禁：发布失败，不能记录为 skipped 后继续；服务端在没有任何可执行用例时返回 409 `ai_evaluation_no_executable_cases`。清单为空（当前状态）时才允许零用例通过，并必须按上面的退役报告如实记录。
- 检查项的判定细节由该用例的 `config_json` 决定；恢复或新增用例时，金额必须能逐项对应 `costPreview`、正式 BOM 或成本明细，模型自行重新分组的、成本引擎未返回的小计仍会使门禁失败。
- 数量为零时，确定性检查同时接受“0 份”和“没有任何历史报价”等明确的等价表达；
  “没有查询到任何报价记录”“没有记录到任何历史报价”“不存在该客户的报价记录”“未检索到历史报价”等完整零结果结论也接受；含糊、假设、疑问或双重否定（例如“并不是没有报价”）不能通过。
- 门禁失败不会删除数据，也不会主动停止已经健康启动的服务。

最新机器报告：

```text
logs/ai-release-gate-latest.json
```

完整且无筛选的正式配方目录可以证明目标配方不存在，因而其报告无法读取；此外，配方 API 按名称/规格不区分大小写的包含匹配规则，原目标名称中的纯 ASCII 字母数字（可含连字符）片段若完整返回零条，且只有 keyword 筛选、正式请求路径与回执一致，也可证明目标缺失。其他筛选、截断、缺失名称或已有目标的列表不能作此证明。此等价证据仍要求回答明确说明原目标资料不可用，不接受替代对象资料；同一句明确说明候选“均不含/不是”原目标属于排除候选，不算替换目标，明确说明候选“不能作为该目标的数据来源”也属于排除；其他句继续使用候选资料或转折肯定仍拒绝。“档案不存在，无法提供数据”是正常缺失结论；“不存在无法提供报告的问题”仍视为反转，不予通过。

## 5. 失败后的处理

1. 打开“管理看板 → 今日待办”，找到“AI 回归检查有 N 项未通过”。
2. 进入“知识库 → AI 治理”查看失败用例和检查依据。
3. 判断是知识数据过期、纠正规则不准确、AI 未调用正确工具，还是模型服务异常。
4. 修复对应数据或规则。
5. 重新运行发布门禁；页面手动检查只用于确认修复效果，不能替代内部发布门禁记录。
6. 最新一次内部发布门禁全部通过后，管理待办会自动消失。

涉及模板配置成本能力的改动，除固定核心门禁外，还必须用本次缺陷的真实问句做专项验收，确认工具链包含正式模板解析和 `build_recipe_bom_draft`，回答成本等于响应中的 `costPreview.currentTotalCost`，包装角色没有遗漏或重复，并在最终回答中明确复述完整模板、`12-120`、带浮球、木箱和珍珠棉。若回答展示分项，逐项金额必须来自 `costPreview.details` 或正式 BOM，不能由模型另算分类小计；工具内部参数正确但回答遗漏配置条件或出现无法追溯的金额都视为失败。专项验收是代码任务证据，不替代固定核心发布门禁。

## 6. 能力边界

- 这不是让 AI 自由改写业务规则；只有用户明确提交的正确做法才能进入长期学习。
- 回归测试不会修改订单、配方、成本、库存或知识内容，只记录检查运行和结果。
- 回归通过只能证明已定义的检查条件满足，不能证明 AI 在所有未知问题上绝对正确。
- 本页反馈流程中的用户纠错不会自动升级为运行规则或发布门禁，避免错误经验被固化；清单非空时，清单要求的系统检查参与发布门禁，当前清单为空（2026-09-19 旧用例退役），因此发布流程目前没有自动 AI 质量拦截，恢复需要按当前真实实体重新编写用例并做一次显式清单变更。
- 外部 AI 服务不可用时门禁会失败，因为本阶段验证的是“真实 AI 当前可用且回答正确”。
